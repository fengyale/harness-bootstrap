# <特性名> 变更记录

> 由 `request-analysis` 技能在阶段 1–2 产出；部署后在末尾补「部署记录」。
> **本文件由 `scripts\harness-start.ps1` 自动创建，直接就地填写并提交，不要另存副本**；
> 只有不用 `harness-start`、手工建记录时，才把本模板复制到 `.harness/changes/<特性名>/summary.md`。
> **L0 不建记录；L1 只写 `.harness/changes/_small.md` 一行；L2 / L3 才用本模板建目录。**
> 「待补短板」只记 harness 能力（规则 / 门禁 / 技能 / 模块卡）；纯业务改动写「无」即可通过阶段 6。

## 分两段写（不许一次成稿）

1. **阶段 1：先落盘** —— 填完「第一阶段」后跑
   `scripts/check-summary.ps1 -Feature <特性名> -Stage initial`；通过后**单独提交一次**
   （该提交只包含 `.harness/` 下的文件），再开始改代码。
   `harness-start` 已替你建好文件并跑过阶段 1：首跑通常因占位符未填而 `Gate result: BLOCKED`，
   补完字段与三节内容后重跑，看到 `Gate result: OPEN` 再动代码。
2. **阶段 5–10：收尾** —— 补「验证方式 / 评审结论 / 部署记录 / 待沉淀」，再填「第二阶段」字段。

> pre-commit 会拒绝「**新增** summary + `.harness/` 之外的改动」同一个提交（合并 / 压缩合并除外）。
> 它只能看提交、看不到编辑顺序：**先提交代码、再单独提交 summary 不会被本地 hook 拦住**，
> 这条工序靠流程本身保证；已存在的 summary 后续与代码一起提交不受影响。

## 第一阶段：先落盘（动代码前必填）

- 日期：`YYYY-MM-DD`（`metrics.ps1` 按这个日期分窗口；不写就退回文件修改时间并标 undated）
- 加载技能：`loaded_skills: <request-analysis, coding-skill>`（记录**全流程**加载过的技能；收尾前再核一次，中后段的 `sql-review` / `expert-reviewer` / 评审子智能体也要补上。列出的技能必须真实存在于 `.harness/skills/`，否则 `check-summary` 会 WARN；项目已安装的 core 技能 `request-analysis` / `coding-skill` / `expert-reviewer` 在阶段 10 应出现在列表，确实跳过就写 `load_skip_reason`。每次真正调用技能时用 `scripts\record-skill.ps1 -Skill <名>` 记一条，阶段 10 会对「声明但没有调用记录」的技能报 WARN）
- 未加载技能原因：`load_skip_reason: <一句话；loaded_skills 为 none 时必填>`
- 触及模块：`touched_modules: <module1, module2>`
- 流程档位：`flow: <L2|L3>`（L2 标准 / L3 完整，判据见 `.harness/rules/开发流程规范.md` 第 1.1 节；L1 不建本文件，只写 `_small.md`）

> 这一段和下面三节一起过 `-Stage initial`：**功能点与验收标准 / 影响面（或技术变更清单）/ 任务拆分**必须是真的内容，留模板占位符（`<…>`）会直接失败。只填字段不填这三节，等于没做需求分析。

## 第二阶段：收尾（阶段 5–10 再填）

- 教训编号：`lesson_id: <kebab-case 如 xml-dollar-brace> -- <一句话摘要>`（`corrections ≥ 1` 时必填具体 id；没有教训写 `-`）
- SQL 评审：`sql_review: TODO(涉及 SQL 时必填：表名 / 语法 / 结构 / 绑定 / 结果 / 计划 / 结论；结论为「通过 / 已改写」时必须引用 .harness/changes/ 下本特性 sql-review/ 目录里真实存在的证据文件（EXPLAIN 或结果摘要）；无 SQL 写"无 SQL 变更")`
- 纠正次数：`corrections: <N>`（收尾时按实际填；不是先写 0 再改，写之前在对话里数一遍）
- 实现层纠正：`impl_corrections: <N>`（属于实现细节的纠正数；没有就填 0，不能大于 `corrections`）
- 交付状态：`delivery_status: <已交付未提交|已提交未部署|已部署|不适用>`（终态用它表达「没部署 / 不适用」，不要留空；写 `已部署` 时部署记录必须有至少一行真实内容）
- 测试跳过原因：`test_skip_reason: <没有可执行测试命令时必填一句话；有测试命令写 ->`（阶段 5/7 无测试命令时，没有这句话会 FAIL；有这句话才降为 WARN）
- 跨仓记录：`linked_records: <repo:path 或 URL，多个用逗号分隔；无跨仓记录写 ->`（每个仓库各留一份 summary，这里指向另一个仓库的记录；门禁不校验对方仓库是否存在）

> 两个阶段的字段由 `scripts/check-summary.ps1` 分档校验：**阶段 1 与 pre-commit 查档位 / 加载技能 / 触及模块 + 上面三节内容**；
> **`corrections` / `impl_corrections` / `lesson_id` / `sql_review` / `delivery_status` / `linked_records` 由阶段 10 查**——它们只有做完才知道，提前写只能写假数。
> **缺字段、留占位符、内容节只有表头 = 任务未完成。**
>
> `lesson_id` 是"第 2 次才落盘"的机器判据：**每条纠正写一行**（多条就写多行），
> 同一条教训必须复用同一个 id，并在 `--` 后写一句话摘要；**写之前先看
> `.harness/lessons.md`**（`metrics.ps1` 自动刷新、团队共享），同一个坑复用原 id，不要起新名。
> `metrics.ps1` 统计到同一个 id 出现在 ≥2 个任务里时，会直接提示"该升级成规则/门禁/技能"。
> 表里的"任务数"是出现在几个 summary / `_small.md` 行里，不是纠正次数。
