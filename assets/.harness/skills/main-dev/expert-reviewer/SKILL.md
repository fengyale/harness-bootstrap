# 代码评审

> 目标：每个结论都能复核，阻断项有证据，建议项不冒充红线。

## 何时用

- 编码完成、准备合并
- 用户说"审一下 / review / 能不能上"

## 评审范围

- 只看本次 diff 及其直接调用方；未改动代码的问题记为「存量」，不阻断本次合并
- 结论必须带证据：`文件:行` 或命令输出；拿不出证据的写「待验证」，不写「可能有问题」
- 不评价个人风格偏好；同一问题只说一次，不逐行重复

## 模式（跨技术栈不变）

### 六维检查

| 维度 | 必答问题 | 看什么 |
| --- | --- | --- |
| 结构 | 是否落在正确模块与层 | 控制层不写业务；依赖方向是否反向 |
| 红线 | 每条红线是否清零 | 对照项目红线逐条给结论 |
| 性能 | 有没有循环查库、无分页、大事务 | 调用次数与数据量上界 |
| 安全 | 入参是否可信、是否越权、日志是否脱敏 | 资源归属校验、SQL 拼接 |
| 一致性 | 缓存与库的更新顺序、跨模块状态 | 失败时两边是否会对不上 |
| 可测性 | 没测试时，手工验证步骤是否可执行 | 正常路径 + 至少一条失败路径 |

### 分级标准

| 级别 | 判据 | 状态 |
| --- | --- | --- |
| P0（🔴 视觉别名） | 红线未清零；数据错误或丢失；越权 / 敏感信息泄露；不可回滚；构建 / 测试红 | 未修 → 已修（必须）；不允许转待办 / 接受 |
| P1（🟡 视觉别名） | 本次不阻断但有明确代价：公共层缺陷、性能、边界、缺验证、兼容性、存量缺陷影响其他页面 | 未修 → 已修 / 转待办 / 接受 |
| P2 | 命名、可读性、重构建议、注释 | 未修 → 已修 / 转待办 / 接受 / 不适用 |

状态：`未修`（评审刚出，仅阶段 6 允许）/ `已修` / `转待办` / `接受` / `不适用`。

> `✅ 已确认合规` 不是严重度，只写进「六维结论」行；🟢 也不作为严重度。
> 判不准时降级写 P1 并标「待验证」：把建议写成 P0，评审会变成吵架。

### 输出格式

评审结论是 summary.md 的固定表，列顺序不可改：

| 严重度 | 范围 | 状态 | 指纹 | 问题 | 证据 | 处置 |
| --- | --- | --- | --- | --- | --- | --- |
| P0 / P1 / P2 | 本次 / 存量 | 评审者输出 `未修`，实现者更新 | P0/P1 必填 kebab-case，P2 可选 | 一句话说清问题 | 文件:行 或命令 / 路径 | 已修 / 转待办（写清去向）/ 接受（写清理由） |

- 评审者只写 `状态=未修`；`已修` / `转待办` / `接受` / `不适用` 由实现者复核后更新
- 无问题也必须保留一行：严重度 `-`、范围 `-`、状态 `不适用`、指纹 `-`
- 同一张表不能同时出现无问题行和具体发现
- 六维结论写在「六维结论」字段（结构 / 红线 / 性能 / 安全 / 一致性 / 可测性），不进表

### 常见错误

- 只写"看起来没问题" → 没有可复核的结论
- 把风格偏好写成 P0 → 阻断失去意义
- 只审新增行，漏掉被改动的调用方
- 用"建议加测试"代替可测性结论 → 没给出可执行的验证步骤
- 相信作者自述，不跑验证命令
