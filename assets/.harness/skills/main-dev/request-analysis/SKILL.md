# 需求分析

> **硬前置**：L2/L3 任何源码写操作之前，先跑 `scripts\harness-start.ps1 -Feature 特性名 -Requirement "需求原文"`；它没有通过 Stage 1，不得 Edit/Write。L0/L1 先在本节定档并写明记录方式，再走轻量路径。

> 目标：开工前把「做什么、改哪里、怎么算完成」写死，避免边写边想。

## 何时用

- 用户说"加个功能 / 改个逻辑 / 优化一下"，或你准备第一次 Edit/Write 源码
- 需求里出现业务词但含义不明确，或缺陷描述只有现象、没有复现路径

> **先定档，再选记录方式**：按 `.harness/rules/开发流程规范.md` 第 1.1 节选 `L0 / L1 / L2 / L3`。

## 模式（跨技术栈不变）

### 步骤

1. 复述需求，写成**一句可验证的验收描述**（模板见下）
2. 定位模块，列出受影响的接口、表、前端页面、定时任务、消息
3. 与项目硬约束比对，冲突先报，不自行取舍
4. 按档位落盘：L0 不建记录；L1 在 `.harness/changes/_small.md` 追加一行（字段按表头填齐）；L2/L3 **复制** `.harness/changes/_template/summary.md` 到 `.harness/changes/特性名/summary.md`，**功能点与验收标准 / 影响面（或技术变更清单）/ 任务拆分三节必须写成真内容**，留模板占位符等于没做
5. L2/L3 跑 `check-summary.ps1 -Feature 特性名 -Stage initial`；不通过不得开始编码（它现在校验的就是上面三节内容，不是只查字段名）。通过后**单独提交一次**（只含 `.harness/` 下文件），再进入编码。L1 的 `_small.md` 行由 `metrics.ps1` 解析，提交时 pre-commit 会核对 diff 是否真的没超过 1 文件 / 30 行
6. 无法确认的标 `TODO(待确认)`，**开工前只问一次**

### 验收描述模板

> 当「角色」在「场景」执行「动作」时，系统「可观测结果」；失败时「错误提示 / 状态 / 回滚」。

- ✅「当财务导出跨月订单时，返回的 Excel 含订单号与金额（最小单位），超过 5 万行拆文件」
- ❌「优化导出功能」——没有可观测结果，无法验收

### 定档判据（全部满足才可降档）

| 档位 | 判据 | 记录 |
| --- | --- | --- |
| L0 | 纯文档 / 注释 / 格式 / typo，不改行为 | 无 |
| L1 | 单文件 · diff ≤30 行 · 不碰公共层 / DB / 配置 / 接口 | `_small.md` 一行 |
| L2 | 单模块功能或修复，不跨模块、无 SQL / DDL / 数据迁移 | `summary.md` |
| L3 | 跨模块 / **SQL / DDL / 数据迁移** / 公共层 / 配置开关 / 接口变更 / 上线评审 | `summary.md` + 评审 |

> 拿不准就升档：多写一份 summary 的成本，远低于漏掉影响面。

### 影响面清单（逐项确认，不适用写「无」）

- [ ] 接口：新增 / 修改 / 删除，是否破坏调用方
- [ ] 数据：表结构、索引、历史数据是否要迁移
- [ ] 前端：页面、字段、错误提示
- [ ] 异步：定时任务、消息生产者 / 消费者
- [ ] 权限：谁可以调用，是否涉及资源归属
- [ ] 兼容：灰度、回滚、旧版本客户端

### 什么时候必须停下来问

- 需求有两种合理解释，且实现成本差异大
- 要改公共层、表结构或对外接口
- 与项目红线 / 现有规则冲突
- 验收标准无法观测

其余情况按最保守解释推进，把假设写进记录，不要反复打断。

### 常见错误

- 把方案当需求：「用 Redis 缓存」是实现建议，需求是「查询要在 200ms 内返回」
- 术语按字面理解，与代码实体对不上
- 只列接口不列表，改到一半才发现要迁移
- 漏掉定时任务 / 消息消费者等非 HTTP 入口
