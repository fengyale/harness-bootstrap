# 数据库变更

> 定位：**三阶段怎么拆、大表 DDL 怎么在线做、回填与回滚怎么配**。DDL 红线与回滚触发条件在
> `.harness/rules/数据迁移与回滚.md`；本文只讲做法。变更脚本的目录与执行入口在下方「项目绑定」。

## 何时用

- 上线包含表结构变更或字段语义变更
- 需要给大表做数据订正，担心锁表与耗时
- 变更出问题需要回滚，但没准备反向脚本

## 核心规则（跨技术栈不变）

1. **一次变更只做一件事**：加结构、迁数据、删旧结构，分三次上线
2. **旧代码必须能跑在新结构上**，否则不能先改结构
3. **每条正向脚本配一条反向脚本**，且反向脚本演练过
4. **脚本可重入**：先判断存在性再执行，重复跑不报错
5. **大表变更耗时必须实测**，不靠估算，不在业务高峰执行
6. **上线后核对行数与抽样值**，确认没有静默截断

## Step 1 · 三阶段怎么拆

| 变更类型 | 锁 / 重写风险 | 阶段划分 |
| --- | --- | --- |
| 加可空列、加普通索引 | 低（支持在线 DDL 时） | 一次完成：扩展，旧代码照常运行 |
| 改列类型、加非空、加默认值 | 高，可能全表重写 | 扩展 → 迁移 → 收缩，三步分开上线 |
| 拆表或合并表 | 高 | 双写 → 回填 → 读切新 → 停旧写 → 删旧 |
| 字段语义变更（同一列换含义） | 高 | 新列双写 → 回填 → 读切新 → 删旧列 |
| 纯数据订正（批量修值） | 中，取决于批量 | 分批回填 + 校验脚本，不成对删改结构 |

> 判定顺序错了后面全错：先看这次变更会不会锁表或重写，再决定拆成几步。

## Step 2 · 大表 DDL 的在线方案

- 先确认数据库版本支持哪些在线 DDL 操作，把"不锁表"和"会重写表"的操作分清
- 不支持在线 DDL 时用影子表或在线变更工具，变更期间用双写或触发器保持同步
- 优先避免整表重写的操作：改类型、加非空默认值、改字符集
- DDL 排在低峰窗口执行，先在同等数据量的环境演练并记录真实耗时
- 执行期间盯锁等待与主从延迟，超过阈值立即中止

## Step 3 · 回填与双写

- 回填按主键区间分批，每批固定条数加短间隔，避免长事务与主从延迟
- 回填可断点续跑：记录已处理的最大主键，中断后从断点继续
- 双写期以新列或新表为准，旧列继续写但不再读；切读要能一键切回
- 回填前后跑校验脚本：条数、空值率、抽样比对
- 回填完成并稳定观察一个周期，才进入收缩阶段

## Step 4 · 回滚与上线顺序

- 正向与反向脚本同一目录、同一次提交，成对命名
- 反向脚本必须先在演练环境执行一遍，记录耗时与影响面
- 上线顺序写进变更说明：扩结构 → 发布兼容代码 → 回填 → 切读 → 收缩
- 收缩阶段删列或删表前，确认没有旧版本实例还在运行
- 上线后核对行数、抽样关键值、主从一致性

## 自检清单

- [ ] 脚本重复执行结果一致且不报错
- [ ] 每条变更都有对应回滚脚本，且已执行过一遍
- [ ] 大表变更的实际耗时已测，不靠估算
- [ ] 发布顺序在变更说明里写明，且分阶段
- [ ] 回填可断点续跑，分批且有进度记录
- [ ] 删除旧列前确认旧版本代码已下线
- [ ] 上线后行数与抽样值已核对

## 常见错误

- 直接改列类型或加非空约束 → 全表重写与长锁，业务不可用
- 回滚脚本最后补写 → 从未被执行验证，真出事时跑不通
- 先删旧列 → 仍在运行的旧版本代码立即报错
- 一条脚本混做加列、回填、删列 → 出问题无法只回滚其中一步
- 收缩与代码发布同一批上线 → 两侧只能一起回滚，风险叠加
