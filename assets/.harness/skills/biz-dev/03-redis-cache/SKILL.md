# 缓存

> 定位：**什么时候该缓存、读写怎么写、坏了怎么办**。边界判据在 `.harness/rules/缓存与一致性.md`，
> 本文只讲做法。项目的入口名 / Key / TTL 在下方「项目绑定」，可照抄的真实代码在「项目实证」。

## 何时用

- 高频读、接口变慢、要降数据库压力
- 已有缓存出现不一致 / 脏读
- 做缓存预热、批量失效、热点 Key 防护

## 核心规则（跨技术栈不变）

1. **缓存只加速，不承载正确性**：缓存丢了业务必须还能跑
2. **缓存故障必须降级**：捕获后走库，记 `warn` 带 Key，不把缓存故障变成业务故障
3. **写路径：先改库，事务提交后删缓存**；不要更新缓存，也不要"先删再提交"
4. **Key 必须可定位、可批量失效**：有统一前缀，变量部分用 `{id}` 这种占位形态
5. **不设永久 Key**，除非在规则文件里登记过理由

## Step 1 · 先判断该不该缓存

| 数据特性 | 策略 | TTL 量级 |
| --- | --- | --- |
| 读多写少、可容忍秒级旧值 | Cache-Aside（查缓存 → miss 查库 → 回填） | 10–30 min |
| 热点数据、可预热 | 启动预热 + 定时刷新 | 永久 + 主动更新 |
| 强一致（余额 / 库存 / 权限） | 不做普通缓存；必须做就走原子操作 + 版本校验 | ≤1 min 或不用 |
| 写多读少 | 不缓存，先优化 SQL 与索引 | — |
| 结果不可重复计算（外部计费） | 先算清重算成本再决定 | — |

> 判定顺序错了后面全错：先确认"能不能容忍旧值"，再谈 Key 和 TTL。

## Step 2 · 读路径的形状

1. 取缓存；命中即返回。**缓存异常要捕获并当作 miss**，不要抛给调用方
2. miss → 查库；查不到 → 写空值标记（短 TTL），防穿透
3. 查到 → 组装返回值 → 回填；TTL 带随机抖动，避免整点失效

## Step 3 · 写路径的形状

1. 事务内更新库（`rollbackFor` 必须声明）
2. **事务提交后**删缓存；提交前删会被并发读把旧值回填
3. 删除失败要重试或进补偿队列，不能只打一行日志

## Step 4 · 三类故障的处置

| 故障 | 现象 | 手段 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，请求全打到库 | 空值标记（短 TTL）/ 入参校验 / 布隆过滤器 |
| 击穿 | 热点 Key 过期瞬间并发回源 | 单飞（进程内）/ 分布式锁 |
| 雪崩 | 大量 Key 同时过期或缓存整体不可用 | TTL 随机化 / 本地缓存兜底 / 限流降级 |

## Step 5 · 列表与聚合缓存（谨慎）

- 只在数据变更频率极低时使用；失效按前缀重建，不逐条猜 Key
- 分页列表的 Key 必须带查询条件与分页参数，否则会串结果

## 自检清单

- [ ] 每个 Key 有前缀与 TTL
- [ ] 所有缓存操作被 try-catch 包裹，异常走库
- [ ] 写路径是「改库 → 提交 → 删缓存」
- [ ] 查不到的数据有短 TTL 空值标记
- [ ] 热点 Key 有击穿保护，TTL 不同时过期
- [ ] 没有 `KEYS`，没有「查出来再 set 回去」的更新缓存写法
- [ ] 缓存里没有未处理的敏感信息

## 常见错误

- 先删缓存再更新库 → 并发读把旧值回填
- 事务未提交就删缓存 → 回滚后缓存已被清空
- 所有 Key 同一 TTL → 整点雪崩
- 把缓存当存储 → 缓存丢了业务不可用
- 用缓存掩盖缺索引的慢查询
