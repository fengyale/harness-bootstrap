# 事务与一致性

> 定位：**事务边界画在哪、回滚范围多大、跨服务失败怎么补**。判据在
> `.harness/rules/缓存与一致性.md` 与 `.harness/rules/消息与异步.md`；本文只讲做法。
> 项目的事务原语与既有写法在下方「项目绑定」。

## 何时用

- 一次改动写多张表、调外部接口、或更新缓存
- 跨服务写入需要保证最终一致
- 同一请求可能重复提交或被重复消费

## 核心规则（跨技术栈不变）

1. **事务只包本地库写入**；远程调用、发消息、缓存更新一律移出事务
2. **事务必须声明回滚范围**，受检异常也要回滚，默认值不是"全部异常"
3. **事务内不做大循环、文件读写、远程查询**；长事务比偶发不一致更伤系统
4. **跨服务只认三种方案**：本地消息表、补偿、对账；不追两阶段提交式的强一致
5. **需要幂等的地方用业务唯一键**，一个业务动作一个键，键由服务端生成
6. **事务边界写在服务层**，接口层只做参数绑定，不组织事务

## Step 1 · 先选一致性方案

| 参与方 | 典型场景 | 方案 |
| --- | --- | --- |
| 单库多表 | 订单 + 明细、主表 + 扩展表 | 本地事务，一次提交，多写少查 |
| 本地库 + 消息 | 提交后要通知下游 | 本地消息表：同事务写业务与消息记录，轮询重发 |
| 本地写入 + 远程接口 | 调第三方或别的服务 | 先本地提交，再调用；失败进补偿队列或对账 |
| 跨服务扣减 | 库存、余额、额度 | 预留或冻结额度 + 确认 / 取消两条路径 |
| 多个异构存储 | 关系库 + 文档库 + 搜索引擎 | 尽量拆掉；必须保留时以业务对账为准，不追强一致 |

> 判定顺序错了后面全错：先数"谁必须原子"，再选方案，最后才写注解。

## Step 2 · 画事务边界

- 从"哪几条写必须同生共死"开始，不是从注解开始
- 只读查询不进事务；查询里夹带写入（如顺带更新统计）要拆出去
- 事务内只做写库与必要的本地校验，查库次数越少越好
- 嵌套调用先确认传播行为，不要默认"内层一定会加入外层事务"

## Step 3 · 回滚范围

- 回滚声明的异常类型要覆盖受检异常；只声明运行时异常会漏掉回滚
- 捕获异常后不再抛出等于主动放弃回滚，必须在代码里显式注明理由
- 回滚后要清理已产生的外部副作用：已写缓存、已生成临时文件、已发出的消息
- 唯一约束冲突、乐观锁失败这类并发错误不重试整个事务，返回可判定的业务错误

## Step 4 · 跨服务失败的补偿形状

- 每一步先记录"已完成"（本地状态表），再调下一步；状态是补偿的依据
- 补偿动作必须幂等且可重入，同一个业务键执行两次结果一致
- 补偿有状态与次数，超限转人工工单，不留无限重试
- 对账是最后防线：按天比对关键余额与数量，差异生成待处理清单
- 补偿与重放都写审计，出问题能定位停在哪一步

## 自检清单

- [ ] 事务边界包含全部必需写入，且不含远程调用
- [ ] 回滚范围覆盖受检异常，吞异常处已显式注明
- [ ] 缓存与消息的更新发生在事务提交之后
- [ ] 重复提交或重复消费有业务唯一键，且有唯一约束兜底
- [ ] 跨服务写入的每一步都对应一条补偿或一项对账
- [ ] 补偿动作幂等、可重入、有次数上限
- [ ] 事务内没有大循环、文件读写或远程查询

## 常见错误

- 事务内调远程接口 → 长事务拖住连接池，且远程失败无法回滚
- 先删缓存再提交事务 → 并发读把旧值回填
- 只包了一半写入 → 半提交，靠人工补数据
- 捕获异常后不再抛出 → 事务提交了本该回滚的数据
- 补偿不做幂等 → 重放两次就扣两次
