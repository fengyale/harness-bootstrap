# 分页查询

> 定位：**页码还是游标、count 要不要、索引与排序怎么定、边界怎么返回**。SQL 正确性四层与执行计划要求在
> `.harness/rules/SQL评审规范.md`；本文只讲分页的形状。项目分页写法在下方「项目绑定」。

## 何时用

- 新增或改造列表接口，同时要返回总数与当前页数据
- 深页明显变慢，或被慢查询告警命中
- 前端反馈翻页后数据重复、缺失，或总数与实际条数不符

## 核心规则（跨技术栈不变）

1. **统计与取数共用一份条件构造**，禁止各写一遍
2. **排序必须能唯一确定一行**，用唯一键兜底，否则跨页重复或漏行
3. **分页参数必须有上限**，页大小与偏移都不接受无边界
4. **先过滤、再联表、最后分页**；不要先联多表再截断
5. **空结果、越界、无权限是同一种返回形状**，只差数据与提示

## Step 1 · 页码分页还是游标分页

| 场景 | 数据规模 / 位置 | 做法 |
| --- | --- | --- |
| 后台管理，要跳页，总数要给运营看 | 偏移在万级以内 | 页码分页（offset + limit），照常查 count |
| 深翻页（偏移上万）或高频滚动加载 | 大表 | 游标分页：按唯一键或时间键续取，不带 count |
| 无限滚动，只关心"下一页" | 任意规模 | 游标分页，返回下一页游标 |
| 必须显示总数但表极大 | 千万级 | 页码分页 + 估算总数，界面标注为近似值 |
| 批量导出或离线取全量 | 任意规模 | 分批游标读，不用分页语义 |

> 判定顺序错了后面全错：先看"用户要不要跳页"，再看偏移量级，最后才谈 SQL 写法。

## Step 2 · count 是否必要

- 只有界面明确要"共 N 条 / 总页数"才查 count；不展示就不查
- count 与取数必须条件一致（含软删除、归属、状态过滤），否则总数长期偏大
- 大表 count 慢时，先考虑估算、缓存或改为"是否还有下一页"，不要靠加索引硬顶
- 一次请求只查一次 count；列表内不要对每一行再查关联数据

## Step 3 · 索引与排序

- 过滤列在前、排序列在后组成复合索引，列顺序按选择性排
- 排序字段不在索引里就是全量排序，深页必慢
- 游标分页的键必须唯一且单调；联合键要带全部列做比较，不能只比一列
- 看执行计划确认走了索引与排序消除，不凭经验判断

## Step 4 · 空结果与越界

- 空列表、页码超过总页数：返回空数组加一致的总数，不返回错误
- 页码或页大小越界、非数字：夹到合法范围或显式报参数错，二者选一并写进契约
- 总数为 0 时当前页固定为 1，前端不必特判
- 权限过滤后为空与本来就没有数据，提示文案要能区分

## 自检清单

- [ ] 统计与取数条件完全一致（含软删除、归属、状态）
- [ ] 排序字段组合能唯一确定一行
- [ ] 页大小与偏移都有上限
- [ ] 深页场景的执行计划已核对，未走全量扫描
- [ ] 空结果、越界、无权限返回同一形状
- [ ] 一次请求内没有逐行关联查询
- [ ] 偏移超过阈值时已改游标分页，或写明保留页码分页的理由

## 常见错误

- 统计语句漏掉取数里的过滤条件 → 总数长期偏大
- 用非唯一字段排序 → 翻页出现重复行或漏行
- 先联多表再分页 → 深页代价随偏移线性增长
- 页大小不设上限 → 一次请求拉全表，内存与连接双爆
- count 与列表条件不同步 → 前端页码错乱、最后一页为空
