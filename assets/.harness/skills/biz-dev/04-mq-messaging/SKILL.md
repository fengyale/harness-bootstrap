# 消息生产与消费

> 定位：**该不该异步、幂等键怎么选、发失败与本地消息表、积压怎么处置**。判据在
> `.harness/rules/消息与异步.md`；本文只讲做法。Topic 与消费组命名在下方「项目绑定」。

## 何时用

- 主流程要解耦出异步动作（通知、统计、下游同步）
- 已有消费者出现重复处理、丢消息或无限重试
- 同一业务实体的多个事件必须按发生顺序被处理
- 线上出现积压或消费失败率升高，需要处置

## 核心规则（跨技术栈不变）

1. **消息只描述"发生了什么事"**，不描述"请你替我做业务"
2. **消费必须幂等**：重复投递等于一次效果，且靠唯一约束兜底，不只靠先查再写
3. **发送结果要可判定**；判定不了就进本地消息表或补偿，不靠打日志
4. **可重试与不可重试分开**，重试有上限与退避，超限进死信
5. **契约只增不改语义**，消费端先容忍未知字段，再启用新语义

## Step 1 · 该不该异步

| 主流程与下游的关系 | 一致性 / 延迟要求 | 判断 |
| --- | --- | --- |
| 主流程不关心结果（通知、埋点、审计） | 最终一致，秒级可接受 | 异步，直接发 |
| 主流程要立刻知道成败（扣库存、扣款） | 强一致 | 不做异步；同步调用 + 本地事务 |
| 下游慢但可重试（对账、报表、推送第三方） | 最终一致，分钟级可接受 | 异步 + 重试 + 死信 |
| 峰值写入需要削峰（抢购、批量导入） | 最终一致，可排队 | 队列削峰，消费端限速 |
| 依赖外部系统且 SLA 不稳定 | 最终一致 | 异步 + 补偿 + 人工兜底入口 |

> 先确认"失败晚到能不能接受"，再谈用哪个消息中间件。

## Step 2 · 契约与幂等键

- 事件一次定清：事件名、版本、业务主键、发生时间、变更前后快照
- 幂等键优先用"业务主键 + 事件类型"，**不要用消息 ID**——重发会换新 ID
- 消费端写库前查去重表或唯一索引，最终以唯一约束兜底并发
- 契约字段只增不删；把已有字段改语义等于新事件，要改名加版本

## Step 3 · 发送失败与本地消息表

- 生产端要拿到可判定的发送结果（同步确认或发送回调），不能只 try-catch 打日志
- 业务写入与发送无法同事务时用本地消息表：同事务写业务记录与消息记录，后台轮询重发
- 消息记录要有状态机（待发、已发、失败次数），发送成功置已发，不物理删除
- 轮询重发按时间窗口捞待发与超时未确认的记录；只重试不记状态的方案，进程重启即丢消息

## Step 4 · 重试、死信与积压

- 可重试：网络抖动、下游超时 → 退避重试，到上限进死信
- 不可重试：数据非法、契约不符 → 直接进死信，重试只会堵住后面的事件
- 死信落库可查、可重放；重放必须按业务键去重，不能重复产生业务效果
- 积压先看失败率：失败高先修消费端，再扩并发；保序队列不能简单加并发
- 要保序就按业务键路由到同一分区或队列，消费侧按该键串行

## 自检清单

- [ ] 同一事件重复投递只产生一次业务效果，且有唯一约束保证
- [ ] 发送失败能被发现，不是静默丢弃
- [ ] 业务写入与发送之间的一致性方案已写明（本地消息表 / 事务消息 / 补偿）
- [ ] 可重试与不可重试的错误已分开处理
- [ ] 死信可查询、可重放，且重放幂等
- [ ] 保序事件的键与消费并发设置匹配
- [ ] 契约变更后旧版本消费者仍能解析

## 常见错误

- 消费端先查再写、没有唯一约束 → 并发下仍然重复
- 用消息 ID 做幂等键 → 重发即换 ID，去重完全失效
- 无限重试毒消息 → 堵住队列里后面所有事件
- 事务内直接发消息 → 事务回滚但消息已发出，下游拿到不存在的数据
- 全局并发消费却要求保序 → 顺序实际不成立
