把 AI 编码的约定

Harness Lifecycle 读取一个真实项目，按证据生成 AGENTS.md、规则、技能、门禁和度量。 它把业务模块的重点、难点与风险点沉淀为可复用记录，后续任务无需重复说明；执行不依赖模型记忆，而依赖脚本阻断、字段判定与指标复盘。

重点并非增加提示词，而是让后续业务模块无需重复说明：模块卡、wiki、技能与沉淀记录提供上下文，门禁与指标验证执行结果。
工序随机
同一需求今天写得好、明天写得歪；没有固定入口，人得一直盯着。
上下文污染
常驻文件越堆越厚，真正该读的模块卡、wiki、技能反而读不到。
坑反复踩
纠正只留在对话里，换个模块又犯；第二次还是靠人提醒。
所以这里做的不是“更聪明的提示词”，而是把一次性的说服，变成结构性的约束。 先让工序可预测，再让上下文按需到达，最后让每一次纠正落到规则 / 门禁 / 技能。
01

它是什么

一套装进业务项目的“AI 编码约束系统”。常驻层只放每轮必须读的内容，其余按需加载；拦截点是 git hook 和阶段门，不是编辑器提示。

常驻
AGENTS.md：技术栈、必跑命令、红线、文件索引、必上技能。目标 ≤150 行，每轮都在。
触发
已装技能的 name + description。只有命中当前任务才加载正文，正文不常驻。
引用
技能正文指到的 .harness/rules、wiki、modules；正文让你读时才读。
门禁
pre-commit / stage-gate / metrics：阈值、字段、证据、阶段门，失败即停。

六个动作：触发词与产出

主技能按动作触发；不必背命令，按动作找入口即可。具体命令见「一次任务怎么走」。

03

内部机制

十阶段流水线、评审台账、交付终态、跨仓记录、多模块命令和 git hook，构成了“能判定”的底座。

十阶段

1 需求
一句话 → 验收 / 影响 / 任务；L0/L1 先写明档位。
2 方案
技术方案、风险、回滚；阶段 1–2 可合并执行。
3 编码
按模块命令编译；touched_modules 决定跑哪些行。
4 静态
pre-commit：红线 + SQL + summary 字段。
5 测试
测试命令真跑；退出码非 0 即 BLOCKED。
6 评审
7 列表；P0 已修、P1 有处置；子代理独立上下文。
7 合并
编译 / 测试 / 门禁 / 绕过检测；L2/L3 必过。
8 部署
条件阶段；DDL 要求迁移与回滚成对。
9 验证
上线后验证；delivery_status 表达终态。
10 沉淀
刷新 lessons.md / reviews.md；重复教训必须变成检查。

约束与门禁：六个真实例子

每条约束都应该能回答三个问题：谁检查、什么输入会失败、怎样才算通过。下面是最常被触发的六条。

约束门禁触发示例结果
红线 R4：禁止 @Autowired 字段注入 pre-commit → red-line-scan staged diff 出现 @Autowired private FAIL 提交被拒；改成构造器注入后 PASS
源码提交前必须有记录 pre-commit summary-order / audit-order 提交源码，但没有 summary.md 或 _small.md 行 FAIL 拒绝提交；L0 用 HARNESS_ALLOW_NO_RECORD=1 显式放行
P0 必须已修，P1 必须有处置 stage-gate 6/10 + check-summary P0 状态为 未修，或 P1 转待办 但处置为空 FAIL 阶段 10 不通过；P0 改 已修、P1 写清处置后 PASS
SQL 结论“通过”必须引用证据 check-summary -Stage final sql_review: 通过，但没有 .harness/.../sql-review/... 证据路径 FAIL 只写结论不算通过；补 EXPLAIN 或结果摘要后 PASS
改动模块必须编译 / 测试 stage-gate 3/5 + moduleCommands touched_modules: order，但命令表没有 order 行，也没有 * 默认行 FAIL 缺模块行；补 order 行或 * 默认行后 PASS
开工必须先跑 harness-start（可选） check-task-start（requireTaskStart=true） 提交 summary.md，但没有 .git/harness-task-started 或标记过期 FAIL 拒绝提交；先跑 harness-start 写 marker 后 PASS
约束不是口号。如果一条规则说不出“谁检查、什么输入会失败、怎样才算通过”，它就不该写进 AGENTS.md，而应该留在讨论里。

反过来，结构也会退化成说服。门禁只查“写了没有”，不查“是不是真的”，就只是结构化的说服；所以每条约束必须有失败输入、证据路径和复核点。

多模块：按模块拆分命令

AGENTS.md 的「必跑命令」支持可选模块列。阶段 3/5/7/8 按 summary 的 touched_modules 取并集，逐个模块跑对应命令。

| 用途 | 模块 | 命令 |
| --- | --- | --- |
| 编译 | * | mvn -q -DskipTests package |
| 编译 | order | mvn -q -pl order -am -DskipTests compile |
| 测试 | order | mvn -q -pl order -am test |
* 是默认行；缺模块行且没有 * → FAIL；只有单条命令、没有模块列的旧表只 WARN。单模块项目保持一行一条即可。

04

度量与成长

不把“感觉快了”当结论。四个代理指标 + 旧的 corrections / 技能加载 / lessons，构成复盘依据；无数据时明确标 n/a 或 unknown。

一次通过率
first-pass
任务窗口内没有 blocked 的 scan 占比；没有 gate 事件的任务计 unknown，不算通过。
门禁往返
round-trips
每任务 blocked scan 数；输出 0 / 1 / 2+ 分布与平均值。
Lead time
days
summary 日期 → 记录目录最后一次提交；无提交标 unknown，负值钳到 0。
复用率
reuse
同一技能出现在 ≥2 个任务时，第二个任务的 corrections 或往返是否更低；只出现一次标 n/a。

沉淀回路

summary.md单次记录：评审表、lesson_id、delivery_status
metrics.ps1解析窗口内所有 summary 与 gate.jsonl
lessons.md / reviews.md按 id / 指纹聚合；≥2 次标 promote
晋升规则 / 门禁 / 技能；必须带能变红的检查
阶段 10 自动刷新
从 1.31.25 起，stage-gate -Stage 10 先跑一次普通 metrics.ps1 刷新 lessons.md / reviews.md，再跑 -LessonGate。索引不再只能手动刷新。
四指标仍要主动看
阶段 10 刷新的是索引；四个生产力指标在 metrics.ps1 的输出 / -Json 里。任务收尾后跑一次，或每周复盘跑 -Days 14 -Compare。
reviews.md 是索引，不是单次记录。单次 P0/P1 的真源永远是各自 summary.md 的 7 列表；reviews.md 只回答“这个问题出现过几次、要不要晋升”。
约束的账也要算。开发期用 run-all -Changed 或 -Suite 只跑相关套件；全量并行，墙钟是 max 不是 sum；release.ps1 一次串起版本、verify、zip 和提交消息。 约束不能贵到让人绕过去——bypass rate 升高，等于用脚投票回到“说服”。
05

升级

升级从新包运行引导脚本，绕开项目里的旧 updater；升级后看激活报告，不把 ACTIVE / MANUAL 混在一起。

# 1. dry-run：只看计划，不改文件
powershell -NoProfile -ExecutionPolicy Bypass -File <新包>\assets\upgrade\upgrade-harness.ps1 -Root <项目>

# 2. 执行（推荐保留项目绑定的技能）
powershell -NoProfile -ExecutionPolicy Bypass -File <新包>\assets\upgrade\upgrade-harness.ps1 -Root <项目> -Apply -MergeSkills

# 3. 激活报告：8 项 ACTIVE / MANUAL / MISSING
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\upgrade-report.ps1 -Root . -Strict
upgrade-report
[ACTIVE] 已生效；[MANUAL] 项目还要动（如 requireTaskStart=false、流程规范待填块）；[MISSING] 包内文件缺失。-Strict 有 MISSING 时 exit 1。
多仓升级
assets\upgrade\upgrade-workspace.ps1 + harness.workspace.json 逐仓升级；-Strict 在任一分仓失败、MISSING 或版本不一致时退出 1。

首周怎么落地

不要一次上 25 个技能。先 3–5 个高频模块卡 + 一条主流程，让团队先感受到“不用重复讲”。

Day 1
装新版本，跑 verify-harness / verify-grounding；先确认平台能加载。
Day 2
选 3–5 个高频模块，生成模块卡；每条结论带 E2 证据，不写满 12 个。
Day 3
第一笔 L2 用 harness-start；requireTaskStart 先 false，先看记录和评审表是否顺手。
Week 1
跑 metrics 看四指标；复盘一次 lessons / reviews；团队用顺了再把 requireTaskStart 改 true。
升级项目多一步：reviewLedgerStrict 默认 false，补完第一张评审表后手动改 true；deliveryStatusStrict 同理。

07

最近变化

如果对当前机制尚不熟悉，可先阅读以下七组变化；它们解释了当前入口与记录方式为何与早期版本不同。

评审台账
summary 固定 7 列表；P0 已修、P1 有处置、指纹复用；reviews.md 做跨任务聚合。
测试提速
run-all 并行、六套唯一 TestRoot、-Changed / -Suite、同进程调用；全量从 sum 变 max。
终态与模板裁剪
delivery_status 四值、linked_records、evidence/；删除需求概述 / 与已有特性关系，影响面合并。
开工入口
harness-start 一条命令；requireTaskStart 默认 false，采用后手动 true；check-task-start 只对 summary 提交校验。
多模块编译 / 测试

常见误区

这几条最容易让人“按旧习惯做，然后被门禁拦住”。

把 summary 当 reviews
summary.md 是单次真源；reviews.md 只是索引。评审行没写进 summary，只写在对话里，等于没记录。
以为沉淀不刷新索引
阶段 10 现在会先跑 metrics.ps1 刷新 lessons.md / reviews.md。但四指标仍要主动看 metrics 输出。
以为装了 start 就自动拦
requireTaskStart 默认 false；不手动改 true，pre-commit 不会因为缺 marker 拒你。
把所有模块塞进一条命令
单条固定命令只会覆盖一个模块。用模块列 + * 默认行，阶段 3/5/7/8 才会按 touched_modules 跑全。
让子代理直接落盘
code-reviewer / expert-reviewer 只输出表格，不写文件；复制进 summary 是主 agent 的动作。
以为已经是 YAML
summary.yml 还没实现。当前仍是 summary.md + 正则校验；改模板字段要同步 needles 和测试。
以为门禁绿了就等于对
只写“通过”不挂证据、评审只写自由文本，都会被 SQL 证据 / 评审表拦住；绿的前提是“能失败的东西真的跑过”。
