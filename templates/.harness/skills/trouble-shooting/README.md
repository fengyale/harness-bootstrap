# trouble-shooting —— 线上排查技能集

> **职责**：出事后怎么定位——**现象 → 根因 → 处置**。
> 流程看 `main-dev`；实现看 `biz-dev`。

## 5 个排查场景

| 编号 | 技能 | 触发现象 | 核心手段 |
| --- | --- | --- | --- |
| 01 | `slow-sql` | 接口 > 1s、慢查询告警、DB CPU 高 | EXPLAIN 的 type/Extra、覆盖索引、深分页改造 |
| 02 | `oom-troubleshoot` | `OutOfMemoryError`、Full GC 频繁、进程被杀 | 堆快照分析、泄漏 vs 容量不足 |
| 03 | `cpu-high-troubleshoot` | CPU 持续 90%+、整体变慢无报错 | 线程栈定位热点方法、区分业务线程与 GC 线程 |
| 04 | `mq-backlog-troubleshoot` | 消息积压、消费延迟上涨 | 分清消费慢还是生产暴增、扩前先看下游容量 |
| 05 | `redis-hotkey-troubleshoot` | Redis 单分片 CPU 满、偶发超时 | 热 Key 与大 Key 分开处理，禁止 `KEYS *` |

## 通用处置原则

1. **先止血，后根因**：限流 / 降级 / 扩容 / 回滚，先让用户可用。
2. **先证据，后猜测**：不看线程栈、不看堆快照、不看 EXPLAIN 就说结论，都是在赌。
3. **先区分类型，再找方案**：
   - 内存：泄漏 vs 容量不足
   - CPU：业务线程忙 vs GC 忙
   - 消息：消费慢 vs 生产暴增
   - Redis：热 Key vs 大 Key
   **类型分错，方向全错。**
4. **修完要验证**：压测复现 + 看监控曲线，不能"重启后没再犯"就算完。
5. **留防复发措施**：加监控、加限制、加测试。否则下个月还来。
