# 发布与验证

> **本文件是骨架**：`<!-- slot:… -->` 必须在安装时用项目事实替换，替换不到就整条删除。

## 何时用

- 一次发布同时包含代码、配置或数据结构改动
- 上线后需要判断"是否成功"，而不只是"进程起来了"
- 出现异常需要回滚，但缺可执行的回滚步骤

## 模式（跨技术栈不变）

### 步骤

1. 发布前列变更清单：代码、配置、数据结构、依赖，逐项标可回滚性
2. 定顺序：数据结构兼容变更先于代码，或走新旧双兼容过渡
3. 保留可回滚点（备份或镜像版本），并确认可用的恢复路径
4. 按批次发布，先小流量或单实例，观察后再全量
5. 健康检查分三层：进程就绪、核心接口可用、关键依赖连通
6. 观察窗口内看错误率、时延与日志异常，不看单点是否存活
7. 指标不达标立即回滚，回滚后重跑同一套检查
8. 留存证据：命令、输出、截图、时间点与执行人

### 检查项

- [ ] 变更清单与实际改动完全对应，无遗漏配置项
- [ ] 回滚步骤在非生产环境演练过
- [ ] 健康检查覆盖依赖而不只是端口存活
- [ ] 验证证据可复查，含时间点与操作人
- [ ] 有明确的"回滚判定条件"，不靠临场争论

### 常见错误

- 只发代码，忘记配置与字典开关
- 健康检查只探端口，依赖不通也判成功
- 出问题才开始想回滚步骤，延长故障时长
