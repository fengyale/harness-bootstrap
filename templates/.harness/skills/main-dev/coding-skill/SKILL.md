## 模式（跨技术栈不变）

### 步骤

1. **确认记录已落盘**：L0 无记录；L1 已在 `.harness/changes/_small.md` 追加一行；L2/L3 的 `summary.md` 已存在、`scripts\check-summary.ps1 -Feature <特性> -Stage initial` 通过，且**初始 summary 已单独提交**（该提交只含 `.harness/` 下文件）。在 feature/fix 分支或 `HARNESS_TASK` 下，HEAD 必须已含该特性 summary，否则 pre-commit 会拒绝源码提交。不满足就退回阶段 1
2. 确认模块与包路径
3. **先读同模块一个同类实现**，照它的写法（最可靠的一致性来源）
4. 写最小可用改动；跨模块改动写进 `summary.md` 影响面
5. 编译；编译不过先修编译，不"先放着"
6. 自测：跑必跑命令，并手工走一遍失败路径
7. 红线自查

### 三类改动怎么下手

| 改动类型 | 做法 | 不要做 |
| --- | --- | --- |
| 新增 | 找同类实现照抄结构，只改业务差异 | 自创分层、引入第二套技术栈 |
| 修改 | 先搜调用方，确认行为变更影响面 | 改公共方法签名不查调用方 |
| 重构 | 行为不变为前提，先补测试或验证步骤 | 与需求改动混在同一次提交 |

### 动笔前先定三件事

1. **事务边界**：一次写多表 / 多资源时，失败要整体回滚（见 `.harness/rules/编码规范.md`）
2. **并发与幂等**：同一请求重试会不会写重（消息、回调、支付类必查）
3. **失败路径**：下游超时、缓存不可用、唯一键冲突时返回什么、留什么日志

### 编译 / 测试失败的处理顺序

1. 读完整错误，定位第一个真实错误，不看后续连带报错
2. 同一错误最多修 2 轮；第 3 次仍失败就停下来，报告「已尝试 + 现象 + 怀疑点」
3. 禁止用注释掉代码、跳过测试、`--no-verify` 让门禁变绿

### 检查项

- [ ] 记录已落盘：L0 无 / L1 有 `_small.md` 行 / L2-L3 有 `summary.md` 且 initial 校验通过
- [ ] 没有新增项目禁止的写法（见红线）
- [ ] 数据访问 / 缓存走统一入口
- [ ] 没有调试残留（临时打印、开关、测试数据）
- [ ] 日志不含敏感信息，关键失败路径有日志
- [ ] 编译通过；测试通过，或写清未跑原因
- [ ] 单次变更 ≤ 文件总量的 40%，超过已拆分

### 常见错误

- 在控制层写业务规则 → 应落在服务层或规则链
- 引入项目没有的第二套技术栈
- 改完只"看了一眼"不编译
- 顺手改无关代码 → 评审无法区分需求改动与格式化
- 为了过编译注释掉测试或校验
