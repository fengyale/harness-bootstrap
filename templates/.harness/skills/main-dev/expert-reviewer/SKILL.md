# 代码评审

> **本文件是骨架**：`<!-- slot:… -->` 必须在安装时用项目事实替换。
> 目标：每个结论都能复核，阻断项有证据，建议项不冒充红线。

## 何时用

- 编码完成、准备合并
- 用户说"审一下 / review / 能不能上"

- 项目红线清单：<!-- slot:redlines -->
- 本项目高发的额外检查项：<!-- slot:extra.checks -->
- 评审结论写回位置：<!-- slot:review.output -->

## 评审范围

- 只看本次 diff 及其直接调用方；未改动代码的问题记为「存量」，不阻断本次合并
- 结论必须带证据：`文件:行` 或命令输出；拿不出证据的写「待验证」，不写「可能有问题」
- 不评价个人风格偏好；同一问题只说一次，不逐行重复

## 模式（跨技术栈不变）

### 六维检查

| 维度 | 必答问题 | 看什么 |
| --- | --- | --- |
| 结构 | 是否落在正确模块与层 | 控制层不写业务；依赖方向是否反向 |
| 红线 | 每条红线是否清零 | 对照项目红线逐条给结论 |
| 性能 | 有没有循环查库、无分页、大事务 | 调用次数与数据量上界 |
| 安全 | 入参是否可信、是否越权、日志是否脱敏 | 资源归属校验、SQL 拼接 |
| 一致性 | 缓存与库的更新顺序、跨模块状态 | 失败时两边是否会对不上 |
| 可测性 | 没测试时，手工验证步骤是否可执行 | 正常路径 + 至少一条失败路径 |

### 分级标准

| 级别 | 判据 | 处理 |
| --- | --- | --- |
| 🔴 阻断 | 红线未清零；数据错误或丢失；越权 / 敏感信息泄露；不可回滚 | 修完重新评审 |
| 🟡 建议 | 性能隐患、可读性、缺测试、边界未覆盖 | 记录理由与代价，不阻断 |
| ✅ 通过 | 六维逐项有结论，且已执行验证命令 | 附实际检查项 |

> 判不准时降级为 🟡 并写「待验证」：把建议写成阻断，评审会变成吵架。

### 输出格式

```
结论：🔴 N 项 / 🟡 M 项 / ✅ K 项
🔴 文件:行 — 问题 — 依据（红线 / 规则）— 修复建议
🟡 文件:行 — 问题 — 代价 — 可选方案
验证：<实际跑过的命令与结果>
存量（不阻断）：<本次未改动但发现的问题>
```

### 常见错误

- 只写"看起来没问题" → 没有可复核的结论
- 把风格偏好写成 🔴 → 阻断失去意义
- 只审新增行，漏掉被改动的调用方
- 用"建议加测试"代替可测性结论 → 没给出可执行的验证步骤
- 相信作者自述，不跑验证命令
