## 何时用

- 高频读、接口变慢、需要降低数据库压力
- 已有缓存出现不一致

## 模式（跨技术栈不变）

### 步骤

1. 判断是否值得缓存（读多写少 vs 强实时）
2. 设计 key（模块前缀 + 业务标识）与 TTL
3. 读：先查缓存，miss 再查库并回填
4. 写：**先更新库，事务提交后再删缓存**（不要先删再提交）
5. 防护：空值占位短 TTL（穿透）；热点 key 加互斥（击穿）；TTL 加随机抖动（雪崩）

### 检查项

- [ ] 只走统一缓存入口
- [ ] key 可读、可定位、可清理
- [ ] TTL 有值，批量写入不在同一秒过期
- [ ] 删缓存在事务提交后

### 常见错误

- 先删缓存再更新库 → 并发脏读窗口
- key 只用业务 id → 跨模块撞 key
- 所有 key 同一 TTL → 同时失效引发雪崩
