# 开发流程规范

> **定位**：阶段流程、质量门（退出条件）、回滚路线、变更管理与 **AI 编码纪律**。
> **分工声明**：流程管控由 `main-dev` 技能承担（阶段 1–3、5–9 各有对应技能，阶段 4 由 pre-commit 自动执行、阶段 10 无专属技能，按本节与 `summary.md` 执行）；具体编码模式见 `biz-dev` 技能；线上问题排查见 `trouble-shooting` 技能。
> ⚠️ 生成说明：阶段数量按项目实际调整（小项目可合并 1–2），但 **L2/L3 的 `summary.md`、L1 的 `_small.md` 一行、红线检查、冒烟验证不可省**。质量门必须**可判定**。

---

## 一、阶段流水线（十阶段）

> **编号是机器判据**：`scripts\stage-gate.ps1` 的 `-Stage N` 与下表一一对应（阶段名同源）。
> 改名可以，改编号不行——改编号要同步 `stage-gate-rules.json` 与 `summary.md` 模板。

| 阶段 | 名称 | 使用技能 | 质量门（退出条件） | 产出 |
| --- | --- | --- | --- | --- |
| 1 | 需求分析 | `request-analysis` | 功能点有编号、验收标准可验证、澄清项已闭环；`summary.md` 已建立且 `check-summary.ps1 -Stage initial` 通过 | `.harness/changes/<特性>/summary.md`（先建骨架） |
| 2 | 方案设计（含任务拆分） | `request-analysis` | 技术变更清单完整、风险有预案、任务粒度 **≤4h** 且已评估 40% 阈值 | 同上（技术变更清单 / 任务拆分章节） |
| 3 | 编码实现 | `coding-skill` + `biz-dev/*` | 变更量 ≤40%、**编译通过**；新增行不得违反 🔴 红线 | 可编译代码 |
| 4 | 静态检查 | —（pre-commit 自动） | 红线扫描 0 violation（只算新增行）、门禁已安装且最近一次扫描通过 | `.harness/metrics/gate.jsonl` |
| 5 | 测试（单元 + 集成） | `unit-test-write` | 单元：全绿、关键逻辑覆盖达标；集成：受影响链路的真实返回 / 计划 / 截图，至少一项有记录；都没有须写明原因 | `summary.md`「验证方式」 |
| 6 | 代码评审 | `expert-reviewer` | 6 维度都过、**无 🔴 问题**；**评审后若有代码修改，必须回到第 5 步重测** | `summary.md`「评审结论」 |
| 7 | 合并（含质量门禁） | `unit-test-ci` | 评审通过 + 编译 / 测试（单元 + 集成）/ 覆盖率 / **红线扫描** 全绿 + 工作区干净 | 合并记录 |
| 8 | 部署（条件） | `deploy-verify` | 迁移已在 test 验证、`db-migrations.sql` 与 `rollback.sql` 成对、部署成功 + 版本记录 | `summary.md`「部署记录」 |
| 9 | 验证（条件） | `deploy-verify` | 冒烟通过、观测期（如 30 分钟）内指标正常、回滚方案可执行 | 观测结论 |
| 10 | 沉淀 | — | 计数块与全部字段完整、教训去向已写（规则 / 门禁 / 技能 / 模块卡） | `summary.md`「待沉淀」 |

> **先落盘再动手**：L2/L3 的第一产出是 `summary.md` 骨架，L1 的第一产出是 `_small.md` 一行；不是代码。
> L2/L3 的 `check-summary.ps1 -Stage initial` 不通过不得进入阶段 3；L1 的字段按 `_small.md` 表头填齐。
> **初始 summary 必须单独提交一次**（该提交只含 `.harness/` 下的文件），再提交代码：git 看不到编辑顺序，
> 只能拿提交顺序当证据；`pre-commit` 会拒绝「新增 summary + `.harness/` 之外的改动」同一个提交（合并 / 压缩合并除外）。
> 本地 hook 只能判定「同一次提交里是否混排」：**先提交代码、再单独提交 summary 不会被它拦住**，这条工序靠流程本身；
> 历史顺序的审计需要在 CI 对提交区间检查。`git commit --amend` 会在提交后按同一规则审计并记录告警。
> replay（合并 / 压缩合并 / cherry-pick / rebase）被门禁拦下后，请用 `git reset --hard`、`git reset --mixed`
> 或 `--abort` 清理；只撤销暂存（`git reset HEAD -- .`）会留下 replay 状态文件。
> `/plan` 模式的计划必须复制进 summary（L2/L3）或 `_small.md` 的说明列（L1），不能只留在工具的计划面板。
>
> **第 4 步不是手动步骤**：`pre-commit` 对本次提交的新增行跑红线扫描，失败即拒提交；
> 阶段门只读 `gate.jsonl` 的最近一次结果，**不重跑全量扫描**（存量违规会让门永远 BLOCKED）。
> **第 8–9 是条件阶段**：只有 L3 且确实要发布时才走；L1 在 `_small.md` 说明列写「未涉及部署」，L2 在 `summary.md` 写「未涉及部署」。
> **第 5 步同时含单元与集成**；合并后在主干再跑一次全量集成属于回归，不算阶段。
> **阶段 1–2 可合并执行**（方案与任务拆分写在同一轮），但 L2/L3 的 `summary.md`、L1 的 `_small.md` 一行不可省；L0 不建记录。

### 1.1 四档链路（先定档，再走阶段）

| 档 | 判定条件（任一不满足就升档） | 走哪些阶段 | 跳过怎么处理 |
| --- | --- | --- | --- |
| **L0 记录** | 纯文档 / 注释 / 格式 / typo；不改代码行为、不碰公共层、无 SQL / 配置 / 接口 | 1 定档 → 3 改 → 5 必要验证 → 7 合并 | 不建 `summary`、不写 `_small.md`；出现纠正 / 教训立即升 L1 |
| **L1 轻量** | ① 单文件 ② diff ≤ 30 行 ③ 不碰公共层 / 基础设施层 ④ 无 SQL / DDL / 数据迁移 ⑤ 无配置 ⑥ 不新增接口或表 | 1 定档 → 3 编码 → 5 测试 → 7 合并（4 由 pre-commit 自动；2 写一句话；6 用自检清单） | **不建 `summary` 目录；只在 `.harness/changes/_small.md` 追加一行；不跑依赖 summary 的 `stage-gate` 1/3/5/6/10**；阶段 8–10 不适用 |
| **L2 标准** | 普通功能 / 缺陷修复，单模块 | 1 → 2 → 3 → 5 → 6 → 7 → 10（4 由 pre-commit 自动） | 部署相关写「未涉及部署」 |
| **L3 完整** | ① 跨 ≥2 模块 ② 碰公共层 / 基础设施层 ③ SQL / DDL / 数据迁移 ④ 改配置开关 ⑤ 需要上线 | 1–10 全阶段 | 无跳过 |

- 定档结果：L0 不建记录；L1 写进 `_small.md`；L2/L3 写进 `summary.md`：`flow: L2`。拿不准就**升档**。
- 档位不是永久标签：过程中触发 L3 条件，立即升档并在 summary 记一行。
- 安装时必须把本表的判据按项目实际改名（"公共层"对应项目的哪些 module、配置在哪个目录）。

### 技能可能没装全（**按这张表降级，不要跳检查**）

首次落地通常只装 3–5 个技能。下表里"使用技能"列提到的技能**可能不存在**，
此时按"降级做法"执行——**技能可以缺，检查不能缺**：

| 阶段 | 技能没装时的降级做法 |
| --- | --- |
| 1–2 | 没有 `request-analysis`：L0/L1 按 1.1 定档（L0 不记录、L1 写 `_small.md` 一行）；L2/L3 手工写 `summary.md`，功能点必须编号、验收标准必须可验证、任务 ≤4h |
| 3 | 没有 `coding-skill`：按 `.harness/rules/工程结构.md` 分层，改完必须过编译 |
| 3–7（涉及 SQL 时） | 没有 `sql-review`：按 `.harness/rules/SQL评审规范.md` 手工评审，并把结论写进 `summary.md` 的 `sql_review:` |
| 5 | 没有 `unit-test-write`：至少手工验证改动路径，并在 `summary.md` 记录验证方式 |
| 6 | 没有 `expert-reviewer`：对照 `.harness/rules/编码规范.md` 红线逐条自查，六维结论仍要写进 `summary.md` |
| 7 | 没有 `unit-test-ci`：手工跑编译 + `scripts\red-line-scan.ps1` |
| 8–9 | 没有 `deploy-verify`：按本项目既有发布流程走，但要记录部署版本与冒烟结果 |
| 10 | 没有对应技能：按 `references` 式沉淀清单写「待沉淀 + 去向」，字段仍由 `check-summary.ps1` 校验 |

## 二、阶段衔接规则

### 2.1 阶段门（机制，不是建议）

从第 N 阶段进 N+1 之前，先跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\stage-gate.ps1 -Stage N -Feature <特性名>
```

| 输出 | 含义 | 该怎么做 |
| --- | --- | --- |
| `Gate result: OPEN` | 客观条件全部满足 | 可以进入下一阶段 |
| `Gate result: BLOCKED` | 有 AUTO 项未通过 | **禁止**进入下一阶段，先修 FAIL 行 |
| 单行 `[SKIP]` | 该判据已声明但未实测（占位 / 标注不适用） | 不计为通过；交付说明里必须点名 |

说明：

- 标 `HUMAN` 的项（如"用户确认了方案"）无法从磁盘判定，只提示、不阻断。
- **门禁按阶段分级**：提交时只校验可判定的基础产物字段（pre-commit `Stage initial`）；`lesson_id` / `sql_review` 等收尾字段在阶段 10 校验（`Stage final`）。不以"是否做过某动作"作为判据，除非有可判定的产物证据。
- 标 `AUTO` 的编译 / 测试判据会**真的执行 `AGENTS.md` 必跑命令表里的那一条**（阶段 3/5/7/8）：
  - 行存在且已填实测命令 → 真跑，退出码非 0 即 BLOCKED；
  - 行存在但仍是占位符或标了「待实测 / 不适用」→ `[SKIP]`，不阻断也不假装通过；
  - **整行缺失 → BLOCKED**（没声明 ≠ 声明了没填，先把行补上）。
- 阶段门是**无状态**的：每次现算，不维护"当前到第几步"，换工具换机器都不失效。
- 它只做一件事：**让"能不能往下走"变成客观事实，而不是自觉**。
- `red-lines` 判据读 `.harness/metrics/gate.jsonl` 的**最近一次 scan**，不跑全量扫描（存量违规会让门永远 BLOCKED）。
- **L2 / L3 合并前跑一次 `-Stage 7`**；L1 仍需正常合并，但**不跑依赖 `summary.md` 的阶段门（1/3/5/6/10）**，用 `_small.md` 一行 + 编译/测试/红线扫描作为判据。阶段门不替代 pre-commit，自动门禁仍是红线扫描 + SQL 评审。


- **串行推进**：上一阶段质量门未满足，**禁止进入下一阶段**。
- **小改动可合并**：涉及文件很少时阶段 1–2 可合并执行，但 **L2/L3 的 `summary.md`、L1 的 `_small.md` 一行不可省；L0 不建记录。红线检查与冒烟验证任何场景不可省**。
- **回退**：出问题按下方「回滚路线」退到对应阶段。

## 三、分支与提交规范

- 分支：`feature/<特性名>`（**与 `.harness/changes/<特性名>` 同名**）、`fix/<问题描述>`。
- 主干为保护分支，**只接受合并请求**，且必须：阶段 6 评审通过 + CI 全绿。
- 提交信息：`<type>(<scope>): <message>`，type 取值 `<feat|fix|refactor|test|docs|chore>`。

## 四、回滚路线

| 阶段 | 回滚手段 | 触发条件 |
| --- | --- | --- |
| 3 编码实现 | `<如 git checkout -->` | 改错方向 |
| 5 测试 | 回到阶段 3 修复 | 测试失败率超阈值 |
| 6 评审 | 修复后重新评审（改过代码须回阶段 5 重测） | 🔴 问题未清零 |
| 7 合并 | 回退上一稳定版本 | 合并后主干验证失败 |
| 8 部署 | 回退上一版本产物 + 执行 `rollback.sql` | 部署失败 |
| 9 验证 | 回滚 + 降级 | 错误率超阈值 |

> **数据库变更的回滚不在本表范围**：必须使用 `.harness/changes/<特性>/rollback.sql`，
> 且**代码回滚先于数据修复**。

## 五、变更管理

```
.harness/changes/
├── _small.md             （L1 小改滚动记录：一行一次；L0 不写）
├── <特性名>/             （L2 / L3）
│   ├── summary.md        （必须）
│   ├── db-migrations.sql （有 DDL/DML 变更时必须有）
│   └── rollback.sql      （与上面成对，缺一不可）
```

`summary.md` **只有一个模板**：`.harness/changes/_template/summary.md`，复制后填写；L1 不建目录，只追加 `_small.md` 一行。
**不要按记忆另写格式**——章节名是机器判据，改名即视为缺失：

| 章节 / 字段 | 被谁读 |
| --- | --- |
| 「需求概述」（或「为什么」） | `stage-gate` 阶段 1 |
| 「技术变更清单」「冲突与风险」「任务拆分」 | `stage-gate` 阶段 2 |
| 「验证方式」 | `stage-gate` 阶段 5 |
| 「评审结论」「待补短板」 | `stage-gate` 阶段 6 |
| 「回滚方案」 | `stage-gate` 阶段 9 |
| 「部署记录」 | 部署后回写（`changes/README.md` 第 4 条） |
| 「待沉淀」 | `stage-gate` 阶段 10 |
| 计数块（`loaded_skills` / `flow` / `corrections` / `impl_corrections` / `touched_modules` / `lesson_id` / `sql_review`） | `scripts/check-summary.ps1`（阶段 1 与 pre-commit 查基础字段；阶段 10 查收尾字段） |
| `load_skip_reason` | `scripts/check-summary.ps1`（`loaded_skills: none` 时必填；有技能加载可留空） |

## 六、AI 编码纪律（**本节是给智能体的操作约束，不是给建议**）

### 6.1 变更量阈值

- **单次变更 ≤ 文件总量的 40%**，超过必须拆分批次。
- 每次操作后**必须验证**：`<编译命令>` / `<类型检查命令>`。

### 6.2 上下文加载约束

- 编码前默认只读「本任务涉及的模块卡 + 直接相关的 1–2 份 wiki / 规则」；**技能与模块卡不占此额度**，按流程必上。
- 跨模块改造 / 数据迁移 / 上线评审可超限，但须在 `summary.md` 写一行「额外读取：… ｜ 原因：…」。
- **具体做法优先查技能**；规则文件只定义边界，**不重复展开模式细节**。

### 6.3 质量检查点

| 检查点 | 通过标准 |
| --- | --- |
| 编译 / 类型检查 | 0 error |
| 红线扫描 | 0 🔴 violation |
| 单元测试 | 全绿；关键逻辑覆盖率 `<≥80% 或 100%>` |
| 评审 | 0 🔴 issue |
| CI | 全绿 |

### 6.4 红线冲突处理

违反根 `AGENTS.md` 的红线时：**立即停止 → 修复 → 从受影响阶段重新验证**。
**禁止"先合入后续再改"。**

### 6.5 熵管理周期表（防文档与代码腐化）

| 周期 | 动作 |
| --- | --- |
| 每日 | 红线扫描（`scripts/red-line-scan.ps1`） |
| 每周 | 依赖审计 |
| 每两周 | 架构审视（对照 `工程结构.md`）+ **退役候选**：`metrics.ps1 -Days 28` 报 `retire candidate`（技能创建 ≥28 天且窗口内 0 加载）的只列清单，**人确认后**才删 |
| 每月 | 技术债清理 + **技能体检**（是否与代码同步、是否长期不触发、`description` 是否还能命中；结果需人确认） |
| 每季度 | 重构 + **技能矩阵结构审视**（技术栈 / 架构变了没有）；删除动作一律走上面双周节奏，本行不另设删除 |

### 6.6 新增规则 / wiki 必须写明触发者

**每条新增的规则或 wiki，必须同时写清它靠什么被加载或执行**：哪条必读路径、哪个技能、或哪道门禁。

- 写不出触发者的，**不许落盘**——否则就是"写了没人读"的死文档
- 只写进文档、没有任何读取路径的规则，等于没写
- 能做成门禁的，优先做成门禁（`scripts/red-line-rules.json`），不要只留在文字里
