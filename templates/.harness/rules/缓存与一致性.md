# 缓存与一致性

> **定位**：什么时候该上缓存、缓存与库怎么保持一致、缓存故障时业务怎么活。
> 具体写法见技能 `biz-dev/03-redis-cache`；本文只定义边界与判据，不重复实现。
> 本项目没有缓存时**整份删除**（与 SQL 规则同一处理方式）。

## 1. 先判断该不该缓存

| 场景 | 结论 |
| --- | --- |
| 读多写少、可容忍秒级旧值 | 适合缓存 |
| 强一致（余额、库存扣减、权限） | 不做普通缓存；必须缓存时走原子操作 + 版本校验 |
| 写多读少 | 不缓存，先优化 SQL 与索引 |
| 结果不可重复计算（外部计费） | 先确认失败重算成本，再决定是否缓存 |

> 缓存是性能手段，不是正确性手段。用缓存掩盖慢查询，问题会在缓存故障时集中爆发。

## 2. Key 与生命周期

- 🔴 Key 必须有统一前缀：`<项目前缀>:<模块>:<业务>:<标识>`（与红线 R2 一致）
- 🔴 必须设置 TTL；永久 Key 要在 `.harness/rules/编码规范.md` 登记理由
- 批量失效用 `SCAN`，禁止 `KEYS`
- 同一业务对象的多个 Key 使用同一版本号，避免部分失效
- Key 里不放原始敏感信息（手机号、身份证），必要时先哈希

## 3. 一致性策略

- 默认顺序：**先更新库，再删除缓存**；不要更新缓存
- 删除失败要重试或进补偿队列，不能只打一行日志
- 读写并发导致的旧值回填：可接受时用短 TTL 兜底；不可接受时用版本号或延迟双删，并在 `summary.md` 写清依据
- 跨库事务不把缓存写进事务；缓存只由本模块负责
- 批量更新后按前缀失效，不要逐条猜 Key

## 4. 三类故障预案

| 故障 | 现象 | 必备手段 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，请求全打到库 | 空值缓存（短 TTL）/ 布隆过滤器 / 入参校验 |
| 击穿 | 热点 Key 过期瞬间并发回源 | 单飞（进程内）/ 分布式锁 |
| 雪崩 | 大量 Key 同时过期或缓存整体不可用 | TTL 随机化 / 本地缓存兜底 / 限流降级 |

- 🔴 缓存异常必须降级：捕获后走库，不让缓存故障变成业务故障
- 降级要记 `warn` 日志并带 Key，便于统计影响面
- 降级不能静默：连续失败要能被告警发现

## 5. 自检清单

- [ ] 每个 Key 有前缀与 TTL
- [ ] 写路径是「更新库 → 删除缓存」
- [ ] 缓存读写异常被捕获并降级
- [ ] 热点 Key 有击穿保护
- [ ] 失效逻辑可重跑（幂等）
- [ ] 没有 `KEYS`，没有「查出来再 set 回去」的更新缓存写法
- [ ] 缓存里没有未经处理的敏感信息

## 6. 常见错误

- 先删缓存再更新库 → 并发读把旧值回填
- 缓存与库双写，没有失败补偿
- TTL 全部设成同一时刻 → 整点雪崩
- 把缓存当存储，缓存丢了业务不可用
- 用缓存解决本应加索引的慢查询
