# 数据迁移与回滚

> **定位**：表结构变更与数据回填的顺序、兼容窗口、回滚条件。
> 迁移脚本与回滚脚本必须成对放在 `.harness/changes/<特性>/`，并随代码一起评审。
> 本项目没有数据库时**整份删除**（与 `sqlGate=false` 口径一致）。

## 1. 四条原则

- **增量**：只前进，不改历史脚本；已执行的脚本不回头修改
- **可重复执行**：脚本重复跑结果一致（幂等）
- **可回滚**：每个迁移有对应回滚，且真的演练过
- **可观测**：迁移后有校验查询，结果写进 `summary.md` 的「验证方式」

## 2. 三阶段：扩展 → 迁移 → 收缩

1. **扩展**：加新字段 / 新表，旧代码不受影响（可空、有默认值）
2. **迁移**：双写 + 分批回填 + 校验一致
3. **收缩**：切换读路径、观察一个发布周期后，再删旧字段

> 🔴 禁止一步到位：加非空字段、改字段类型、删字段与代码发布同批上线。

## 3. DDL 红线

- 🔴 大表加 `NOT NULL` 字段必须有默认值，或先可空后回填
- 🔴 改字段类型 / 长度前先确认现有数据不越界
- 🔴 删字段 / 删表前确认没有代码、报表、外部系统引用
- 大表加索引 / 改结构用 online 或并发方式：`<!-- slot:db.online.ddl -->`
- 锁表时间与执行窗口要提前说明，避开业务高峰

## 4. 数据回填

- 按主键分批（建议 500–1000 行），可断点续跑
- 回填幂等：重复执行不产生重复数据（用唯一键或覆盖写）
- 限速，避免拖垮主库；观察主从延迟与慢查询
- 双写期间以新字段还是旧字段为准，必须写清，不能两边都"最新"
- 回填失败可重跑，失败批次能定位

## 5. 校验

- 行数对比：新旧表 / 字段 `count` 一致
- 抽样对比：按业务主键抽 20–50 条逐字段比对
- 聚合校验：金额合计、状态分布、关键业务指标
- 校验 SQL 与结果写进 `summary.md`；不一致时先停下，不要继续切读

## 6. 回滚

- 🔴 回滚脚本与迁移脚本同目录、成对存在
- 回滚可重入；默认不删用户数据，只回退结构与开关
- 明确回滚触发条件（错误率、延迟、校验不一致、业务反馈）
- 回滚后缓存要一起失效，避免读到迁移期间写入的旧结构
- 回滚演练结果要记录；没演练过的回滚视为不存在

## 7. 发布顺序

`迁移 → 应用（兼容新旧）→ 校验 → 清理旧结构`，每一步都能独立回滚。

## 8. 自检清单

- [ ] 迁移与回滚脚本成对存在，且都演练过
- [ ] DDL 在旧代码下可运行（可空 / 有默认值）
- [ ] 回填分批、幂等、可断点续跑
- [ ] 有行数、抽样或聚合校验，并记录结果
- [ ] 回滚触发条件与执行人明确
- [ ] 清理旧结构安排在观察期之后

## 9. 常见错误

- 迁移与代码同一次发布，出问题无法单独回退
- 回填脚本没有分批，长事务锁表
- 回滚脚本没验证过，真出事跑不通
- 只校验行数，不校验金额 / 状态
- 先删旧字段再切读路径，回滚时数据已丢
