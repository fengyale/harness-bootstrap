# 消息与异步

> **定位**：什么时候该用异步、消息怎么保证不丢不重、消费失败怎么收场。
> 具体写法见技能 `biz-dev/04-mq-messaging`；本文只定义边界与判据。
> 本项目没有消息中间件时**整份删除**。

## 1. 该不该异步

| 场景 | 结论 |
| --- | --- |
| 主流程不依赖结果、可最终一致（通知、统计、日志） | 用消息 |
| 必须立刻返回结果（下单校验、扣款） | 同步调用 |
| 只是想让接口"快一点" | 先查慢在哪，不要直接丢消息 |
| 跨系统强一致 | 消息不解决，走事务或对账 |

> 异步换的是响应时间，付出的是可观测性与一致性成本；没有补偿与对账方案的异步不要上线。

## 2. 生产者

- 🔴 发送失败必须处理：重试 + 记日志 + 告警，禁止静默吞掉
- 消息体必须带业务主键、事件类型、发生时间、追踪 ID；不塞大对象与敏感信息
- 与本地事务的边界：先落库再发，或本地消息表 / 事务消息；不允许「消息发成功、库回滚」
- Topic 命名：`<项目前缀>-<模块>-<事件>`；消费组：`<项目前缀>-<模块>-<动作>-group`
- 发送失败可重试，但重试要有上限，避免把线程拖死

## 3. 消费者

- 🔴 必须幂等：幂等键 + 去重表 / 唯一索引；重复消费不产生副作用
- 消费失败抛异常交框架重试，禁止 catch 后返回成功
- 重试要有上限与退避，超过进死信；死信必须有人处理，不能只积压
- 顺序敏感的消息：同一业务主键落同一分区 / 队列，并在代码注释里写明依据
- 积压时先扩消费能力或降级，不要盲目重置位点
- 消费入口打 `info` 日志，记录业务主键与消息 ID

## 4. 兼容与发布

- 消息体只增字段、不删不改语义；新增字段必须可选且有默认行为
- 先升级消费者，再升级生产者
- 消费逻辑变更要能处理历史消息，或明确跳过策略并记录
- 下线事件前确认没有在线消费者：查消费组订阅，不要只看代码

## 5. 自检清单

- [ ] 消费逻辑有幂等键与去重手段
- [ ] 生产发送失败有重试 + 日志 + 告警
- [ ] 消息体带业务主键与追踪 ID
- [ ] 消费失败会抛异常，不会被吞
- [ ] 死信有负责人与处理记录
- [ ] 消息体变更向后兼容
- [ ] 本地事务与发送顺序明确，不会「发成功、库回滚」

## 6. 常见错误

- 消费端 catch 后打日志当成功 → 消息丢失
- 没有幂等键，重试写重
- 消息体只有一段文本，排查时无法定位业务对象
- 生产者在事务提交前发送
- 把需要强一致的操作拆成异步，又没有对账
