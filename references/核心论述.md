# 核心论述（SKILL.md 的下沉部分）

> 这些内容只在**首次搭框架 / 遇到争议 / 排查环境坑**时读一次。主 SKILL.md 只保留流程与判据，避免每次触发都全量进上下文。

## 第零部分：基调（**这是不能丢的东西，后面所有判断都服从于它**）

Harness 不是"更聪明的提示词"，是给 AI 编程加的**外部约束系统**：约束边界、规定输入、仪表观测、外部判据、可重复。
模型能力不是瓶颈，**可预测性**才是；同一个需求今天写得好、明天写得歪，人就得一直盯着——那不叫工程化。

所有机制只服务三句话，后文任何判断与它冲突时，以这三句为准：

1. **实现层的错由机器吸收，人只确认关键决策。** 能机器判定的绝不留给人提醒；人只看业务取舍与红线冲突。
2. **每一次纠正必须落到「规则 / 门禁 / 技能」三者之一。** 只在对话里说"下次注意"等于没发生；第二次还犯，就是机制缺失。
3. **项目知识必须在该被读到的时刻被读到；读不到就由出口校验拦回来。** 常驻层只放每轮必读的索引，细节按需加载；漏读由 `check-summary`、阶段门、`verify-*` 在出口发现。

## 1.2 为什么现在不行（病根）

普通 AI 编码工具给的是**通用脚手架**：它知道怎么写 Java、怎么写 React，
但它**不知道你这个项目**：不知道金额只能用分、不知道你们的异常体系、不知道缓存 Key 有前缀、
不知道该先写 `summary.md`、不知道哪一步必须停下来给人确认。

于是这些"项目知识"只能靠人**每轮临时补给**——这就是"来回太极"的根源。

**Harness 做的事：把这些隐性的项目知识，变成显性的、可加载的、可校验的资产。**

## 1.4 四条核心思想（不可动摇）

> **最初的公式：Harness = 规则 + 执行引擎 + 闭环反馈。**
> 下面四条就是它的展开：①②是"规则怎么组织"，③是"知识怎么留存"，④是"系统怎么自愈"。

无论项目技术栈怎么变、文件怎么组织，这四条不能变——变了就不是 harness 了：

**① 分层约束：常驻 / 按需 / 强制**

| 层 | 作用 | 载体 | 约束力 |
| --- | --- | --- | --- |
| **常驻** | 每轮都在场的最小底线：技术栈、红线、索引 | 根 `AGENTS.md`（薄） | 参考 |
| **按需** | 到具体场景才知道的"怎么做"：规程、模板、排查路径 | 技能（`SKILL.md`） | 参考 |
| **强制** | 不靠自觉、机器判定、过不去就停下 | 脚本 + git hook + CI | **强制** |

> **规则管"怎么做对"，机制管"不这么做就过不去"。**
> 只写规则不做门禁，这套东西的价值兑现不了——这是它最常见的失败方式。

**② 渐进披露：常驻要薄，厚的按需**

上下文是有限资源。常驻文件每轮都占 token，所以只能放"每轮都必须知道"的；
凡是"到某个场景才需要"的，一律下沉成技能，让它按需加载。

**③ 项目知识必须落盘，不能留在对话里**

会话不继承。这次对话里摸出来的经验，不写进文件就等于丢了。
所以：**约定落盘，别留在对话里。**

**④ 闭环反馈：这套东西必须能自己变好**

这是最初定义里的第三个支柱——**Harness = 规则 + 执行引擎 + 闭环反馈**。
前三条讲了规则怎么放、引擎怎么跑；这一条讲**它怎么不至于烂掉**。

没有闭环，前三条都会腐化：
规则会过时、技能会与代码失真、门禁会变成"反正也没拦过"的装饰。
**与代码不同步的技能，比没有技能更坏——它会自信地教错。**

闭环的四个环节，缺一不可：

| 环节 | 在这个框架里是什么 | 载体 |
| --- | --- | --- |
| **① 证据** | 每次改动留下可查的记录：改了什么、为什么、怎么验的 | `.harness/changes/<特性>/summary.md`、编译与扫描的真实输出 |
| **② 判定** | 用**可判定**的标准判断好坏，不靠感觉 | 质量门、A1–A7 验收、红线扫描、覆盖率、`verify-harness.ps1` |
| **③ 修正** | 发现偏差就改：改代码、改规则、改技能 | 沉淀（提示词 B）、技能体检（C）、触发调优（D）、补短板（1.6） |
| **④ 沉淀** | 把这次的结论**写回资产**，下次自动生效 | 规则/技能/红线/门禁的更新，而不是留在对话里 |

**判定闭环有没有成的唯一标准：**

> **同一个错误，会不会犯第二次？**
> 会 → 闭环断了（没沉淀，或沉淀了但没生效）
> 不会 → 闭环成立

**这也是"减少人工纠正"能持续的原因**：
人纠正一次是成本；**纠正一次之后框架学会了，才是收益**。
如果每次都要人纠正同一件事，说明我们要建的不是 harness，是一个更听话的 prompt。

**必须可观测，闭环才可能成立。**
所以你不仅要"做对"，还要让"做错了能被看见"：
关键路径要有日志与指标、失败要有明确报错、门禁要有可读输出。
**看不见的问题不会被修，只会被习惯。**

## 1.6 守约定 vs 补短板（**A3 和 A3+ 的分界，最容易走偏**）

A3 要求"符合本项目约定"，但**约定不是天花板**。
一个项目"以前没做缓存"不代表"永远不该做缓存"——那叫**将就**，不叫规范。

#### 两种"不守约定"，一种要罚、一种要奖

| 情形 | 判定 | 做法 |
| --- | --- | --- |
| 项目有明确约定，你没遵守 | ❌ **违规** | 改回来。这是 A3 的红线 |
| 项目**没有**约定，但这是明显缺失（该缓存没缓存、该索引没索引、该幂等没幂等） | ✅ **补漏机会** | 见下方四道闸门 |

#### 补短板的四道闸门（**必须全过才动手**）

一道不过，就**只提议、不动手**，把理由写进 `summary.md`：

**① 场景闸：这次任务真的会踩到吗？**
- 会踩到 → 可以在本次任务里顺手补（如：这个接口新增了高频查询 → 此时加缓存合理）
- 不会踩到 → **不要顺手重构**。记进 `TODO(建议升级)`，等有场景时再做
- > 你改的是一个正在跑的项目，**没有场景支撑的改造成本远大于收益**

**② 价值闸：补了之后，收益能被说清吗？**
- ✅ "这个列表接口 QPS 最高，没缓存直接压库"
- ✅ "这个消费者会重复消费，没幂等会重复扣款"
- ❌ "加上缓存比较专业"——这是**没有收益**的改造，别做

**③ 成本闸：改动范围可控吗？**
- 只影响本次要动的模块 → 做
- 要动全项目/全链路 → **先提议，单独排期**，不要在业务需求里捎带

**④ 方式闸：补的时候要"融入"，不要"另起一套"**
- ✅ 按项目现有风格补（现有 `RedisConfig` 怎么用，就怎么用）
- ✅ 补完后**回写规则**：新约定要进 `.harness/rules/`，否则下一个人不知道
- ❌ 引入新框架/新范式，跟现有并存两套
- > **补短板 = 在旧地基上加固，不是推倒重建。**

#### 做完必须留痕

补短板必须在 `.harness/changes/<特性>/summary.md` 里写清：

```markdown
#### 顺手补的短板（summary.md 里的写法示例）
| 位置 | 原本的问题 | 这次做了什么 | 依据 |
|---|---|---|---|
| XxxServiceImpl.list | 高频查询无缓存，直压库 | 按 03-redis-cache 加了 Cache-Aside | QPS 最高的 3 个接口之一 |
```

**并且在交付时主动告诉用户**：
> "本次需求之外，我发现 X 处明显短板，在 Y 场景下顺手补了，依据是 Z。如果你不想在本次引入，我可以回退。"

> **宁可提议十次被拒，不要默默改一处。**
> 补短板的前提是**透明**——用户有权决定这次要不要。

#### 这类改造不属于"补短板"

- **大规模重构**（换框架、改分层、迁数据库）→ 这是独立项目，不是顺手活
- **风格偏好**（"我觉得应该用另一种写法"）→ 不是短板，是口味
- **与本次需求无关的优化** → 没有场景，不做



#### 你要带着主观能动性干活

这不是"收到指令、执行指令"的活。**你是在推行一件对的事**，
所以要拿得出判断、提得出方案、扛得住"以前也这样"的惯性。

| 场景 | 消极做法（❌） | 主动做法（✅） |
| --- | --- | --- |
| 项目没有缓存，但新需求是高频查询 | 照着旧代码写，不加缓存 | 按 1.6 四道闸门判断 → 该加就加 → 说明依据 |
| 发现某个消费者不幂等 | 心里知道但不说 | 记进 `summary.md` 的"待补短板"，提示用户 |
| 模板跟项目对不上 | 硬套模板，产出四不像 | 按 `references/自建指南.md` 重新设计 |
| 用户的说法跟核心思想冲突 | 照做（"用户说了算"） | **指出冲突并说明代价**，再让用户决定 |
| 不确定某条约定 | 猜一个看起来合理的 | 标 `TODO(待确认)`，问用户 |

**但这个能动性有边界，越界就是灾难：**

- ❌ **不越权**：不替用户决定业务规则；不做没有场景支撑的大规模重构
- ❌ **不隐瞒**：改了什么、为什么改，必须写在 `summary.md` 里并当面说
- ❌ **不发明**：命令、路径、表名、业务规则，一律以真实项目为准
- ❌ **不放弃核心思想**：可以换实现方式，不能把"受控 / 可判定 / 能自动"丢掉

> **一句话：方法可以协商，目标不能妥协；改动可以大胆，隐瞒绝对不行。**

## 2.3 自成长机制（**框架不是装完就结束，它必须自己长**）

骨架只搭一次，之后靠三个节律维持。**缺了节律，框架三个月就腐化。**

#### 节律一：每次任务后 —— 沉淀（分钟级）

跑 `references/维护与体检.md` 的**提示词 B**，从这次任务里提炼。

**判据**：同一条纠正出现 **第 2 次** 才值得写；出现 1 次的不写。
（出现 1 次可能只是一次性的事，写成规范反而增加噪音）

**并给这条教训一个固定的 `lesson_id`（写进本次 `summary.md`；L1 写进 `_small.md` 的教训列）**：
写前先看 `.harness/lessons.md`（团队共享、可提交），第二次遇到必须复用同一个 id（并在 `--` 后写一句话摘要），
`metrics.ps1` 统计到同一个 id ≥2 次会直接提示"该升级成规则/门禁/技能"——
判据从"靠人记得"变成"脚本数得出"。

#### 节律二：每两周 —— 复盘（30 分钟）

跑 `references/两周复盘.md`。**这是验证 A7 的唯一方式。**

只定三个决定：
1. 补哪 **1–2 个**技能（从"重复 ≥2 次但没覆盖"里挑）
2. 哪条从**文档升级成门禁**
3. **删**什么（长期不触发 / 从没拦过的红线 / 已失真的文档）

#### 节律三：每季度 —— 结构审视

- 技能矩阵还是否匹配项目现状？（技术栈变了？架构变了？）
- 规则文件是否过长？该拆的拆、该删的删
- 门禁是否还在生效？（造个违规测一次）

#### 自成长不只是"修"，还要"补"——三件事都要做

| 动作 | 什么时候做 | 例子 |
| --- | --- | --- |
| **修内容** | 发现写错了、过时了、不可判定 | 把"代码要优雅"改成"public 方法必须有 JSDoc" |
| **补文件** | 出现新的知识类型，现有文件装不下 | 举例（这些文件**目前不存在**，是需要时才新建的）：`references/接口变更记录.md`、`.harness/skills/biz-dev/<编号>-<专题>/SKILL.md` |
| **补目录** | 资产长到一定规模，需要分层 | `.harness/skills/` 下新增分类；`.harness/changes/` 按年份分目录 |

> **不要怕改结构。** 框架是给项目用的，项目会变，框架就该跟着变。
> 唯一不能变的是第零部分的基调——**方法可协商，目标不妥协**。

#### 什么时候该警惕

| 信号 | 含义 | 动作 |
| --- | --- | --- |
| 技能只增不减 | 没人做淘汰 | 双周复盘按 `metrics -Days 28` 列候选，人确认后删 |
| 复盘连着两次没有结论 | 复盘流于形式 | 改成只回答"A7 成不成立"一个问句 |
| 规则文件越来越长 | 边界和做法混在一起了 | 把做法拆进技能 |
| 用户开始绕过门禁 | 门禁误报太多 | 收窄 pattern，或降为警告 |
| **同一错误又犯了** | **闭环断了** | 立刻回到"证据→判定→修正→沉淀"，找出断在哪一环 |

## 3.2 冲突与合并策略

| 目标 | 常见情况 | 处理 |
| --- | --- | --- |
| `AGENTS.md` | 可能已存在 | **先读，把内容合并进去**，保留用户原有内容，不覆盖 |
| `CLAUDE.md` | Claude 项目可能有 | 只写一行 `@AGENTS.md` + 技能索引；**不要把规则复制第二份** |
| `.harness/**` | 通常不存在 | 不存在才新建；已存在同名 → 读后合并 |
| `.trae/agents/*.md` | **`.trae/` 通常已存在** | **只新增**；已有 agent 一律保留 |
| `.trae/skills/` | 可能已有技能 | **不要手写内容**，由 `setup-links.ps1` 建联接；同名非联接目录 → 报告不动 |
| `.trae/hooks.json` | 可能已存在且在用 | **默认不动**（模板是空壳 `{ "hooks": {} }`） |
| `scripts/*` | 可能已有同名 | 读后合并；同名是你自己的实现 → 保留你的，我的改名加后缀 |
| `.gitignore` | 几乎一定已存在 | **追加**缺失的行，不整体覆盖 |

#### 3.2.1 `AGENTS.md` 已存在时怎么合并（**最容易出事的一步**）

**合并 ≠ 末尾追加。** 常驻文件的信息架构是固定的五块：
**技术栈 / 必跑命令 / 红线 / 文件索引 / AI 编码纪律**。
合并 = 把现有内容**映射进这五块**，缺哪块补哪块；**内容必须是用户的，结构必须是模板的**。
（`verify-harness` 第 9 项会检查这五块是否齐全——缺一块就是 FAIL。）

0. **重装/增量先出差异清单**（不要一上来就重写）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\agents-delta.ps1
```

输出 `MISSING` / `HOLLOW` / `OK` 三类：**只补前两类，`OK` 的段落一行都不动**。

1. **先完整读一遍**（只读，不改），标出已有章节
2. **分类处理，不要整篇重写**：

| 现有内容 | 处理 |
| --- | --- |
| 事实（技术栈、命令、目录、仓库约定） | 以现有为准；与探测结果冲突时**信现有**，冲突记进交付说明 |
| 规则（红线、编码约定、流程） | 逐条比对；能合并的合并，**语义冲突的列 diff 让人选**，不自行取舍 |
| 无关内容（团队偏好、历史说明） | 原样保留 |

3. **只增不删**：新增内容放进带标记的区块，方便以后定位和更新。**重装前先删掉旧的 marker 区块**，否则会叠加成两份

```html
<!-- harness:begin -->
...本次新增的条目...
<!-- harness:end -->
```

4. **体量**：**只对本次新增区块**做预算——它超过 150 行才下沉到 `.harness/rules/`；**存量内容一行都不动**。常驻层是预算，不是仓库
5. **三不**：不整体覆盖、不静默删除、不改写用户原有表述
6. **交付必须说明**：加了几节、改了哪几条、哪些冲突留给用户决定

## 3.3 本机环境坑（都是实测踩出来的）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 执行策略拦未签名脚本 | 报"未对文件进行数字签名" | 一律用 `powershell -NoProfile -ExecutionPolicy Bypass -File` |
| **PS 5.1 读 `.ps1` 只认 UTF-8 带 BOM** | 脚本里写中文 → **语法错误** | `.ps1` 保持**纯 ASCII**；中文放 JSON（按 UTF-8 显式读） |
| 没有 `pwsh` | `pwsh` 命令不存在 | 用 `powershell`（5.1） |
| `AGENTS.md` 不生效 | 写了但模型不知道 | 设置 → 规则 → 导入设置 → 打开「将 AGENTS.md 包含在上下文中」 |
| 改完规则不生效 | 新旧上下文打架 | **开新对话** |
| 模型沿用旧风格 | 项目里已有大量不合规代码 | 明确告诉它"这是重构" |
| 技能清单有成本 | 技能太多，每轮都占上下文 | 只装用得上的；`description` 短且不撞词 |
| **技能清单被截短** | `description` 太长，尾部触发词丢失 | 触发词**写在最前面**；总长控制在 160 字内 |
