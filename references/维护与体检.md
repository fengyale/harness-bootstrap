# 维护与体检

> 任务做完要沉淀技能时、用户问"接下来怎么维护"时读这份。
> 末尾的「**需要人做的事**」是智能体做不了的，必须明确转告用户。
>
> **提示词编号**（其它文档按编号引用）：**A = 首次落地**（见 `SKILL.md` 2.2 第 2 步）；
> **B = 日常沉淀**（本文第一节）；**C = 技能体检**（第二节）；**D = 触发调优**（第三节）。

---

## 一、日常沉淀（每次任务后执行）

**这是技能矩阵唯一的成长方式。** 骨架只搭一次，矩阵靠这条长出来。

> 每次任务结束先跑 `scripts\metrics.ps1`：`corrections:`、`impl_corrections:` 与 `loaded_skills:` 是删除与晋升的唯一依据。
> 判断"该不该删"要跑 `-Days 28`；只看两三天会把低频但关键的技能误删。

### 1.1 删除（每两周按数据执行）

- 某技能**创建 ≥28 天且最近 28 天 0 次加载**（`metrics.ps1 -Days 28` 报 `retire candidate`）→ **先和人确认，再删目录** + 从 `.harness/skills/README.md` 与 `AGENTS.md` 技能索引同步移除。刚加的技能没遇到对应任务时只会提示 `wait until it is 28 day(s) old`，不要把它当退役候选
- 某红线**28 天 0 次拦截**且抽样确认无遗漏 → 从 `red-line-rules.json`、`AGENTS.md` 红线表、`编码规范.md` 三处同步删除
- 删除前在 `changes/<特性>/summary.md` 记一行"为什么删"，避免下次又加回来

> 脚本只负责"点名候选"，**不负责删**。删除是不可逆动作（尤其在非 git 项目里），必须有人确认。


```text
# 提示词 B：从刚才这次任务中提炼技能（或判定无需提炼）

回顾本次任务全过程，包括我每次纠正你的地方，输出：

1. 我在这次任务里纠正/否决了你几次？每次的原话是什么？
   （只列真实发生过的，不要美化、不要补全）

2. 哪些纠正属于"通用且会再犯"？
   判据：换个模块、换个需求还会犯。只犯一次的不要列。

3. 逐条判断落点，**先出表、再动手**。按这个格式交给我确认：
   | lesson_id | 层次 | 目标文件 | 新建/修改 | 依据（哪条证据） |
   | --- | --- | --- | --- | --- |

   > 落点选不准时先看 `references/落地策略.md` 第三节「干预矩阵」：
   > 高频且能机器判定 → 门禁；高频但判不了 → 技能；只出现一次 → 只记 `lesson_id`。
   落点映射（六类，优先塞进已有文件，不要新开）：
   - **边界/纪律**（"一律不许/必须"，一句话说得完）→ 根 `AGENTS.md` 红线表
     + `.harness/rules/编码规范.md` + `scripts/red-line-rules.json`，**三处编号必须一致**
     （`verify-harness` 第 4 项会校验）
   - **能机械判定**（正则/脚本抓得到）→ `scripts/red-line-rules.json` 加一条；
     先用全库试跑看误报，宁可降级也别让门禁误报
   - **编码细则**（非红线：命名、分层、异常用法、日志写法）→ `.harness/rules/编码规范.md` 正文
   - **事实**（字段/接口/表/术语的真实用法）→ `.harness/wiki/数据模型.md` / `接口协议.md` /
     `业务模型.md` / `领域术语.md`
   - **流程/阶段教训**（怎么检查、何时停、以什么为准）→ `.harness/rules/开发流程规范.md`
   - **场景做法**（这类需求怎么拆、怎么做）→ `.harness/skills/<分类>/<名>/SKILL.md`，
     **优先在已有技能里加一条**，不要为一条经验新开技能

3.1 新建还是修改（**默认修改**）：
   - 已有文件放得下 → 只追加/改写，不新建；同名已存在按 3.2 读后合并，不覆盖
   - 只有"现有文件都放不下，且至少 2 个任务会用到"才新建文件
   - **新建技能门槛更高**：必须已有 ≥2 次同类纠正（同一 `lesson_id` 出现 ≥2 次）；
     否则先写规则或 wiki，不要开技能目录
   - 新建技能时：`name` 与目录名一致、`description` ≤160 字且写清触发场景、
     正文**目标 ≤80 行（硬上限 120 行）**；装完跑 `setup-links.ps1` + `verify-grounding.ps1`

3.5 给每条候选起一个稳定的 `lesson_id`（kebab-case，如 `xml-dollar-brace`），
    写前先看 `.harness/lessons.md`（`metrics.ps1` 自动刷新、团队共享），同一个坑复用原 id；
    **每条候选写一行** `lesson_id: id -- 一句话摘要`（一次任务有多条纠正就写多行），
    写进本次 `summary.md`（L1 写进 `_small.md` 的教训列）；**历史上已有同一教训时，必须复用同一个 id。**
    这是"第 2 次才落盘"的机器判据：`metrics.ps1` 统计到同一 id 出现 ≥2 次，
    会直接提示"该升级成规则/门禁/技能"。没有新教训的这次，写 `lesson_id: -`。

4. 对每条候选，先写"验收标准"：以后怎么判断它真的起作用了？
   写不出来就说明还不该写。

5. 如果确实没有值得沉淀的，明确说"本次无需沉淀"，不要为了产出而编造规范。

最后给出 diff 级别的具体文件改动，并跑一次 scripts\setup-links.ps1。
```

> **判据提醒**：只有"模型会做错、我必须纠正"的地方才值得写。
> 规范和模型默认行为重合的部分不需要写——这决定了你应该**从纠正动作反推**，而不是从知识体系正推。

## 二、技能体检（建议每月，或技能超过 10 个时）

> **evals 解决什么问题**：它回答"**我改了这个技能，到底变好了还是变坏了**"。
> 没有它，技能迭代就是凭感觉调参——改了不知道有用没用，删了不知道有没有损失。
> 官方工具链（跑提示词 × 启用/禁用对比 × 自动打分 × 盲测 A/B）用下面的手工版代替，原理一样。

```text
# 提示词 C：对技能做一次体检（含基线对比）

## 第一部分：静态体检（逐个技能过）
对 .harness/skills/ 下每个技能输出一行：
| 技能 | 最近是否被触发过 | 正文行数 | description 字数 | 与代码是否仍一致 | 建议（保留/改写/删除） |

判定规则：
- 长期不触发 → 要么 description 写得让人看不懂（改写），要么场景不存在（删除）
- 正文过大（>120 行）→ 拆分或把细节下沉到技能内的附属文件
- 与代码不一致 → **最严重**：它会自信地教错，要么立刻改，要么删
- `verify-grounding` 报 `stale`（E2 指向的代码改在技能之后）→ **必须重读那段代码**：
  改技能内容，或确认没变后只更新 `- verified:` 日期；不改日期会一直提醒

## 第二部分：基线对比（挑 1 个最重要的技能做）
1. 给我 5 个真实提示词：3 个应该触发该技能的、2 个不应该触发的。
   如果我没有，你从 .harness/changes/ 的历史特性里挑 5 个真实场景。
2. 每个提示词在**新对话**里跑两遍：一遍该技能启用、一遍禁用。
3. 按这四项打分（各 0-2 分），记录结果：
   - 触发正确性（该触发的触发了 / 不该触发的没触发）
   - 产出是否用了技能里的流程（而不是自由发挥）
   - 产出是否符合技能里的自检清单
   - 产出质量与启用前相比是否更好
4. 汇成表格：提示词 × 启用/禁用 × 得分，并给出一句结论：这个技能值不值得留，哪里该改。

## 禁止
- ❌ 只给"感觉更好了"这种结论，必须有对比数据
- ❌ 用同一个对话跑两遍（上下文会污染，必须新对话）
```

## 三、触发调优（某技能该触发不触发 / 乱触发时）

```text
# 提示词 D：优化某个技能的 description，提高自动触发命中率

目标技能：.harness/skills/<分类>/<技能名>/SKILL.md

1. 先读它的 description，然后**不要看正文**，凭 description 猜测：
   - 它应该在什么场景触发？（列出 5 个真实用户会说的原话）
   - 它**不应该**在什么场景触发？（列出 3 个容易误触发的相邻场景）

2. 给出 8 个测试提示词：5 个应该触发、3 个不应该触发。
   必须用**用户在真实工作里会说的大白话**，不要用书面语。

3. 逐条判断：只看 name + description，这些提示词能不能被正确区分？
   把判断不了的逐条记下来。

4. 针对判断不了的，改写 description。规则：
   - 格式：<做什么 + 关键技术点>。当 <具体场景 / 用户原话> 时使用本技能。
   - 把用户原话直接写进去
   - 必须短（平台会截短 description）
   - 不能和其它技能的触发词重叠（先读一遍所有技能的 description 再改）

5. 输出改前 / 改后对比 + 为什么这样改能提高命中率。改完提醒我：重启工具，并在新对话里验证。
```

## 四、熵管理周期（什么时候做什么）

| 周期 | 动作 | 谁做 |
| --- | --- | --- |
| 每天 | 红线扫描（`red-line-scan.ps1`） | **人**（或 CI 自动） |
| 每周 | 依赖审计 | 人 |
| 每两周 | 架构审视（对照 `工程结构.md`） | 人 + 智能体 |
| 每月 | 技术债清理 + **技能体检**（上面第二节） | 智能体（结果需人确认） |
| 每季度 | 重构 + **技能矩阵结构审视**（技术栈/架构变了没有；淘汰候选一律走 1.1 的双周节奏，不在这里另设删除动作） | **人拍板** |

### 4.1 GitLab CI（可选，把"每天手工扫"变成推送后必跑）

```yaml
harness-check:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  script:
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    - powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-harness.ps1
    - powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-grounding.ps1
    - git diff -U0 "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME...HEAD" | powershell -NoProfile -ExecutionPolicy Bypass -File scripts/red-line-scan.ps1 -Root . -DiffFromStdin
```

- runner 需要 `git` + `powershell`；没有 PowerShell 的 Linux runner 改用 `python3 scripts/red-line-scan.py --diff-file`。
- CI 能兜住"推送后"的绕过：本地 `--no-verify` 的提交到了 MR 仍会被扫。
- **CI 看不到本地绕过率**：`.harness/metrics/gate.jsonl` 被 `.gitignore` 忽略，runner 上没有这份日志。要度量绕过率，得用 GitLab pre-receive hook，或把聚合后的 metrics 文件提交进仓库；不要指望一个 `metrics.ps1` CI job。

## 五、需要人做的事（智能体做不了，必须转告用户）

### 5.1 一次性动作

1. **打开开关**：TRAE → 设置 > 规则 > 导入设置 > 「将 AGENTS.md 包含在上下文中」
   （不打开 `AGENTS.md` 不生效；仅桌面版支持）
2. **重启工具**，确认技能列表里能看到新技能
3. **验证自动触发**：发一句能匹配 description 的话，确认它**真的自己触发了**（不是你以为它在）
4. **装 git 门禁**：`scripts\install-git-hooks.ps1`（需要项目已 `git init`）
5. **门禁自查**：造一个违规 → `git commit` 应被拦 → 删掉 → 应通过
6. **`.gitignore` 补一行**：`.trae/skills/`（联接不进版本库）
7. **换机器/新 clone 后**：跑一次 `scripts\setup-links.ps1`

### 5.2 只能人拍板的决策点

| 决策点 | 为什么智能体不能替你决定 |
| --- | --- |
| **哪几条是真正的零容忍红线** | 智能体可以给建议，但"哪条不能碰"是团队管理决定 |
| **业务规则本身** | 代码里可能没有完整表达（如"取消要退券退积分""每人限领 N 张"），反推不出必须你口述 |
| **每份 wiki 的权威来源** | "冲突时以谁为准"是管理约定，不是技术事实 |
| **哪些历史包袱不能动** | 代码里看不出来（为什么这么写、能不能改） |
| **技能删不删** | 体检能给数据，但"这个场景以后还要不要"只有你知道 |
| **是否接受 ToS/合规风险** | 任何"绕过官方限制"的方案，风险都在你的账号上 |

### 5.3 需要定期执行的

见上面第四节「熵管理周期」。其中**每天的红线扫描**可以接进 CI 自动化，其余需要你安排。

## 六、怎么判断这套东西真的在起作用

不要看"文档写得多漂亮"，看这四个信号：

1. **你纠正它的次数在下降**（记一下每周纠正次数，这是最直接的指标）
2. **红线扫描真的拦下过提交**（如果从来没拦下过，要么红线太松，要么门禁没生效）
3. **技能真的被自动触发过**（不是每次都要你手动点名）
4. **改完一个技能，你知道它是变好还是变坏**（说明体检在做）

**一个反信号**：技能越攒越多、谁也不敢删 → 说明体检没做，库在腐化。
