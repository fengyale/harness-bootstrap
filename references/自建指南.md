# 自建指南：模板不适用时，怎么从零设计这个项目的框架

> **`templates/` 是参考样本，不是标准答案。**
> 多数项目跟它长得不一样（不同技术栈、不同分层、不同业务、不同痛点）。
> 这份文档教你**在没有可抄的东西时，怎么自己设计出来**。
>
> **在读这份之前，先读 `SKILL.md` 的第零部分（基调）和 1.6（守约定 vs 补短板）。**
> 那两节定的是"为什么"和"边界"，这份定的是"怎么做"。**方向错了，方法再对也没用。**

---

## 零、设计时的两个基本立场

**立场一：这是给一个具体项目做框架，两种起点，同一目标。**

- **存量加固**（仓库里已有业务代码）：项目有历史包袱、有不一致、有"以前就这么写"的惯性。
  你的任务是**在现状上加固**，不是推倒重建。取证靠读代码（E1/E2）。
- **新项目初始化**（仓库里还没有代码）：没有可读的代码，取证只能靠问对人（E0）。
  先走 `references/新项目初始化.md` 的五轮确认，产出 `.harness/project-brief.md`，
  再按本指南设计文件；代码落地后，E0 逐条升级为 E1/E2。

> 两条路径共用同一套资产结构（规则 / 技能 / wiki / 门禁）和同一套验收标准（A1–A7）。
> 区别只在**证据从哪来**，不在**要建成什么样**。新项目路径的完整流程见
> `references/新项目初始化.md`，这里不重复。
>
> **加固 = 让它可判定、可重复、可交接。** 这条对两种起点都成立。

**立场二：发现短板要补，但不是这次都补。**

"该缓存没缓存"确实是个问题，但**在哪个场景补、补多少、什么时候补**，有明确边界。
判定方法见 `SKILL.md` 1.6 的四道闸门。**这份文档只管"怎么设计",不管"该不该做"——该不该做去 1.6 判。**

## 一、先明确：我们要的到底是什么

不是"一套文档"，是**七个效果 + 一个增量**（见 `SKILL.md` 1.3）。文件只是载体。

| 效果 | 一句话 |
| --- | --- |
| A1 | 先分析再动手 |
| A2 | 会主动加载技能 |
| A3 | 产出符合本项目约定 |
| **A3+** | **该补的短板补上了** |
| A4 | 自己会跑校验 |
| A5 | 有机器门禁 |
| A6 | 用户只需确认关键决策 |
| **A7** | **同一个错误不会犯第二次**（闭环，见 `SKILL.md` 1.4④） |

设计每一个文件前，先问一句：

> **这个东西，是为了让哪一条效果成立？**

- 答不上来 → 不要建
- 答得上来但很勉强 → 优先级放最后

## 二、四种资产，各自解决什么（**这是设计的骨架**）

| 资产 | 解决什么 | 判断依据 |
| --- | --- | --- |
| **规则**（`rules/`） | 限制——**不许怎么做** | 违反代价高、且能判定 |
| **技能**（`skills/`） | 模式——**这类活怎么做** | 反复出现的具体场景 |
| **事实**（`wiki/`） | 背景——**这个项目是什么样** | 不问就不对的那些前提 |
| **门禁**（`scripts/`） | 强制——**不做就过不去** | 能机器判定 |

**关键区别：**
- 规则是**否定式**的（禁止、必须），且**短**——它进常驻文件
- 技能是**肯定式**的（怎么做），且**长**——它按需加载
- 事实是**描述式**的（是什么），**不约束**，只提供背景
- 门禁是**机制**，不是文档——**能判定的规则，一定要落到门禁里**

> 一个常见的错：把"怎么做"写进规则（规则变厚），或把"不许做什么"写进技能（技能触发不到）。
> **边界进规则，做法进技能，背景进事实，能判定的进门禁。**

## 三、从零设计技能集：怎么判断"该有哪些技能"

**不要从技术栈倒推清单**（"Java 项目应该有 CRUD、MQ、缓存……"）——会做出一堆用不上的。

**正确方法：从"用户纠正过什么"倒推。**

### 步骤 1 · 收集整改记录

找这些来源：

- **git log**：`fix`、`hotfix`、`revert` 类提交，看都在修什么
- **代码里的 TODO / FIXME / XXX**：反复出现的主题
- **代码评审留下的意见**（如果有 PR / MR 记录）
- **你自己读代码时发现的"这个写法很危险"**
- **问用户**："这个项目最容易出错的地方是哪儿？"

### 步骤 2 · 聚类

把收集到的整理成表：

| 反复出现的问题 | 出现次数 | 属于哪类 | 该进哪一层 |
| --- | --- | --- | --- |
| 金额用了浮点 | 5 次 commit | 红线 | **规则 + 门禁** |
| 新增模块时目录放错 | 3 次 | 模式 | **技能（crud-scaffold）** |
| 缓存 Key 前缀不统一 | 4 次 | 红线 + 模式 | **规则 + 技能** |
| 不清楚"订单"和"履约单"的区别 | 2 次 | 事实 | **wiki/领域术语** |
| 慢查询没人会看 EXPLAIN | 1 次 | 模式 | **技能（slow-sql）** |

### 步骤 3 · 定优先级

**先做"出现 ≥2 次"的。** 出现 1 次的不做——那可能只是一次性的事。

**首次只建 3–5 个技能。** 参考 `.harness/skills/README.md` 的三分类：
- 流程类（主线：分析 → 编码 → 评审）
- 实现类（这个项目最高频的技术专题）
- 排查类（这个项目最常出的故障）

### 步骤 4 · 命名与编号

- 流程类：不加编号，名字描述阶段（`request-analysis`、`coding-skill`）
- 实现类：加编号，编号代表"优先级/常用度"（`01-xxx` 最常用）
- 排查类：加编号，编号代表事故类型
- **`name` 不带编号**，目录名带（平台规则：目录名 ≠ name 时以 name 为准）

## 四、从零设计规则：什么该进"红线"

### 硬门槛（三条都满足才是红线）

1. **能机器判定**——给得出 grep / 正则 / 脚本动作
2. **违反代价高**——金额错、数据丢、安全事故、线上故障
3. **这个项目真的会犯**——从第三节的"整改记录"里看到苗头

### 数量：**5–8 条**

- 少于 5 条：约束太松，起不到作用
- 多于 8 条：没人记得住，且容易互相冲突
- **宁少勿多**——红线多了就变成"都不是红线"

### 从候选池挑，不要从零想

`references/红线候选池.md` 按技术栈分了组（通用 / Java / Node / Python / Go / DB）。
**先读 `baseline.md` 确认技术栈，再从对应组挑。**

### 每条红线必须三处同步

1. 根 `AGENTS.md` 的红线表
2. `.harness/rules/编码规范.md` 的红线汇总
3. `scripts/red-line-rules.json`

**编号必须一致，不许跳号**（`verify-harness.ps1` 会检查）。

## 五、从零设计 wiki：事实从哪来

四份 wiki 是**这个项目的"是什么"**，只能从代码里挖。

| wiki | 从哪挖 | 挖不到怎么办 |
| --- | --- | --- |
| `领域术语.md` | 类名、枚举名、注释、接口路径里的业务词 | 问用户："这几个词是什么意思、区别是什么" |
| `业务模型.md` | 实体类、关联关系、MQ Topic/Consumer、Redis Key 构造 | 问用户："核心流程是什么" |
| `数据模型.md` | DDL / 迁移脚本 / 实体上的 `@TableName` | 直接抄，不要手画 |
| `接口协议.md` | Controller 的映射注解、DTO 字段 | 抄主链路，不要穷举 |

**每份开头必须有「权威来源声明」**：

> 例：`数据模型.md` ——「**DDL 权威来源**为迁移脚本；本文是同步镜像，不一致时以 sql 为准并回修本文。」

**理由**：与代码不同步的文档**比没有更糟**——它会自信地教错。权威来源声明让"谁对"有裁决规则。

## 六、从零设计门禁：怎么让它真的挡得住

### 门禁的唯一要求：**能失败**

```powershell
# 退出码 0 = 过；非 0 = 不过
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\red-line-scan.ps1
```

### 三层门禁，从便宜到贵

| 层 | 什么时候跑 | 跑什么 | 成本 |
| --- | --- | --- | --- |
| **编辑器内** | 每次改完文件 | 红线扫描 | 秒级 |
| **提交前**（git hook） | `git commit` | 红线扫描 + 编译 | 十秒级 |
| **CI** | 推送到远端 | 编译 + 测试 + 覆盖率 + 红线 | 分钟级 |

**至少要有"提交前"这一层。** 只有 CI 的话，问题发现太晚；只有编辑器内的话，可以绕过。

### 存量项目必须"只拦新增"

见 `references/落地策略.md` 第二节。**这是最重要的操作细节**——
一上来全量拦截，用户会被几百条历史违规劝退。

## 七、自检：设计完问自己六个问题

1. **这套东西里，哪一条能让用户少纠正一次？**——答不出，说明在堆形式
2. **常驻文件我能不能背下来？**——背不下来说明太厚
3. **有没有一条规则是"写了但永远触发不到"？**——有就删
4. **门禁真的会失败吗？**——造一个违规试一次
5. **某个技能如果删掉，会损失什么？**——答不出说明它没用
6. **用户第一次用，会不会觉得"又多了一堆要维护的东西"？**——会的话，说明约束太重、收益不明

---

## 八、最后的提醒

**这套东西的价值不在"齐全"，在"被用到"。**

- 25 个技能全上 → 看起来很完整，实际没人维护
- 3 个技能但每个都真的被触发 → 这才是成功

**宁少勿多。宁可先窄后宽，也不要先宽后废。**
