# 回灌协议（L3：项目 → 模板）

> **一句话**：项目里踩出来的坑，只有**两个独立项目都踩过**，才允许晋升为模板的模式段。
> 一次踩坑留在项目里；跨项目复现才配进包。

---

## 1. 三级回流

| 级别 | 触发 | 落点 | 谁决定 |
| --- | --- | --- | --- |
| **L1 编译** | 每次安装 | 项目内技能正文（绑定层） | 安装器 |
| **L2 沉淀** | 同类纠正在**同一项目第 2 次**出现 | 该技能「本项目坑」小节（带 E2） | 项目负责人 |
| **L3 回灌** | 同一指纹在**≥2 个不同项目**出现 | 包内 `templates/patterns/<id>.md` 的模式段 | 人工确认 |

**L3 永远不许带类名、包名、项目名。** 一旦带上，它就又变成绑定层，换个项目就错。

---

## 2. 指纹

```
<栈键>|<症状码>|<规则或技能 id>
```

例：`orm=jfinal|n-plus-one|slow-sql`

- **栈键**：取自 `stack.json` 的 `field=value`（如 `orm=jfinal`、`mq=none`）
- **症状码**：稳定的小写短语（`n-plus-one`、`cache-avalanche`、`deep-pagination`）
- **id**：对应的技能名或规则编号

同一指纹在不同项目出现 = 该模式有普适性；只在一个项目出现 = 项目特例。

---

## 3. 候选文件格式

放在项目 `.harness/patterns/<id>.md`：

```markdown
id: orm=jfinal|n-plus-one|slow-sql
stack: orm=jfinal
symptom: n-plus-one
projects: 2
version: 1

## 模式

（技术中立：问题是什么、为什么会发生、怎么判断）

## 反例

（最小反例：一两行伪代码，不含项目专名）

## 证据

- 项目 A：现象 + 触发条件（不写项目名，写栈特征）
- 项目 B：同上
```

---

## 4. 晋升流程

```
1. 项目里写候选：.harness/patterns/<id>.md
2. 跑 scripts\promote-pattern.ps1
   - 缺字段 / projects<2 / 缺三节 → FAIL 并列出缺什么
   - 通过 → 复制到 .harness/patterns/outbox/
3. 人工确认（你）：反例是否技术中立、是否真的出现过两次
4. 复制 outbox/<id>.md → 包的 templates/patterns/
5. 在包 VERSION 里记一行来源（项目数、指纹）
```

**脚本不自动写包**：回灌是唯一必须人工把关的环节。

---

## 5. 禁止事项

- 把「项目 A 的类名」写进模式段
- 用 1 个项目的数据就晋升
- 把绑定层（具体 API、命令）放进 patterns
- 晋升后不同步更新模板技能里的模式段（`patterns` 与技能会漂移）

---

## 6. 验收

- 缺 `projects` 或 `<2` → 脚本 FAIL
- 缺三节之一 → FAIL
- 全部通过 → outbox 出现同名文件
- **项目名 / 类名 / 内部代号由人扫一眼确认**——脚本不扫专名，别把这条当成机器保证
