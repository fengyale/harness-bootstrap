# 架构与职责（为什么这么分）

> 这份是给用户解释用的。当用户问"为什么要分 `.harness/` 和 `.trae/` 两处放""为什么组件不在 harness 目录里"时，读这份。

## 一、核心矛盾与解法

用户常见的直觉是：**"既然要搞 Harness，那所有组件就应该都在 `.harness/` 里。"**

这个直觉有一半是对的，但它撞上了一个硬约束：**技能必须能被平台发现，否则它不会被触发——那就成了一堆死文件。**

所以真正的分层是：

| | `.harness/` | `.trae/` |
| --- | --- | --- |
| 谁拥有 | **你**（纯自定义目录） | **工具**（平台的约定目录） |
| 有加载语义吗 | 没有，只靠路径引用被读 | 有：`skills/` 按需索引并**自动触发**；`rules/` 是否注入取决于平台，TRAE 默认不读 |
| 本质 | **知识层**（知识与记录的真源） | **接口层**（入口 / 挂载点） |
| 放什么 | 规范、技能正文、项目事实、变更记录 | 技能入口、校验智能体、门禁配置 |

**判据一句话：**

> 「它需要被 AI **主动发现**吗？」是 → `.trae/`；只是**被引用**的 → `.harness/`

技能**需要被主动发现**（否则不触发）→ 所以 `.trae/skills/` 里必须有它的入口；
但**正文只有一份真源**，住在 `.harness/skills/`。两者用**目录联接**连起来：

```
.harness/skills/biz-dev/redis-cache/SKILL.md   ← 真源（正文在这）
        ▲
        │ 目录联接（mklink /J）
.trae/skills/redis-cache                        ← 入口（平台从这里发现它）
```

- 改文件改的就是真源那一份
- 删掉入口**不会**删真源
- 换工具（Claude Code / Cursor）时，只改链接，不动内容

**这不是 hack：Claude Code 官方文档明确写了技能目录可以是符号链接**，并且"多个位置指向同一目标时只加载一次"。TRAE 侧已实测认目录联接。

### 为什么不能"全放 .trae/"或"全放 .harness/"

| 方案 | 组件住哪 | 触发可靠度 | 跨工具 |
| --- | --- | --- | --- |
| 全放 `.trae/` | 平台目录 | 高 | **差**：换工具要整体搬迁 |
| 全放 `.harness/` + 只靠索引表 | 自己的目录 | **低**：靠模型读到索引后自行判断，会漏 | 最好 |
| **真源 `.harness/` + `.trae/` 放链接** | 自己的目录 | **高**（平台原生匹配） | 好（只改链接） |

第三种就是我们采用的方案。代价只是**每台机器跑一次 `setup-links.ps1`**（联接不跟着 git 走）。

## 二、三层约束力（决定每个文件放哪）

| 层 | 内容 | 载体 | 约束力 | 失效的样子 |
| --- | --- | --- | --- | --- |
| 常驻 | 技术栈、🔴 红线、文件索引 | `AGENTS.md`（规则真源在 `.harness/rules/`，`.trae/rules/` 只是可选平台副本） | **参考** | 写了很多，模型没遵守 |
| 按需 | 编码规范、专项技能、排查手册 | `.harness/skills/*/SKILL.md` | **参考** | 该触发不触发；触发了也不照做 |
| **强制** | 红线扫描、提交前拦截 | `scripts/` 下的脚本 + **git pre-commit 钩子**（`.trae/hooks.json` 只是可选的快速反馈，不算强制层） | **强制** | 跑不过就是过不去 |

> **规则管"怎么做对"，机制管"不这么做就过不去"。**
> 只写规则不做门禁，等于没做——这是整套东西最常见的失败方式。

## 三、三层分工（技能矩阵怎么分类）

| 分类 | 管什么 | 编号含义 |
| --- | --- | --- |
| `main-dev/` | **流程管控**：什么时候做什么、每步门槛 | 与开发阶段一一对应 |
| `biz-dev/` | **具体实现**：这类代码怎么写 | 技术专题编号（01、02…） |
| `trouble-shooting/` | **线上排查**：出事后怎么定位 | 事故类型编号 |

**关键原则：流程技能只定义流程与检查点，不重复展开模式细节；模式细节一律下推到 `biz-dev`。规则文件只定义边界，同样不展开做法。**

## 四、为什么"文档漂移"比"没有文档"更坏

与代码不同步的规范会**自信地教错**。所以每个项目事实文件（`wiki/*`）开头都必须有**权威来源声明**：

> 例：`数据模型.md` ——「**DDL 权威来源**为迁移脚本；本文是同步镜像，两处不一致时**以 sql 文件为准并回修本文**。」

配套三个手段：
1. 每份文档声明**谁是权威、冲突以谁为准**
2. `consistency-verifier` 智能体定期核对代码 vs 文档
3. 变更走 `.harness/changes/`，迁移与回滚成对

## 五、七条纪律

1. `AGENTS.md` **不放进去就不生效**（要打开"包含在上下文中"开关）
2. 新建/修改规则后**开新对话**
3. 项目里已有大量不合规代码时，模型会**沿用旧风格** → 明确说"这是重构"
4. **技能清单每轮都占上下文**（正文才是按需）→ 技能别太多、`description` 要短、**不能撞触发词**
5. 常驻文件必须**薄**（≤150 行）
6. **路径就是接口**：正文与索引里的路径必须与实际一致（含大小写）
7. 与代码不同步的技能**比没有更坏** → 要定期淘汰
