# 平台适配（Platform Adapters）

> **一句话**：内容永远只有一份（`.harness/` + `AGENTS.md`），平台只决定"入口放在哪、用什么方式被发现"。
> 任何编程智能体（TRAE / Claude Code / Codex / CodeBuddy / 未知平台）都走同一套内容，只换入口。

---

## 1. 三条原则

1. **内容与平台解耦**：规则、技能、wiki、脚本都在平台无关的位置；平台目录里**只放入口和链接**，不放正文。
2. **不能用"平台会自动加载"做假设**：技能能否被自动发现因平台而异。不能自动发现的，必须退化为**索引 + 必读清单**。
3. **入口可重建**：平台目录（`.trae/`、`.claude/` 等）里的东西都是**生成物**，删掉能重建；真源永远在 `.harness/`。

---

## 2. 平台矩阵

| 落点 | TRAE | Claude Code | Codex CLI | CodeBuddy | 未知 |
| --- | --- | --- | --- | --- | --- |
| 常驻规则 | `AGENTS.md` | `CLAUDE.md`（用 `@AGENTS.md` 导入） | `AGENTS.md` | `AGENTS.md` | 优先 `AGENTS.md`；平台另有要求再追加一层薄入口 |
| 技能发现 | `.trae/skills/<name>`（目录联接） | `.claude/skills/<name>`（链接或复制） | `.codex/skills/<name>`（链接或复制） | `.codebuddy/skills/<name>`（链接或复制） | 无自动发现 → 索引导航 |
| 子智能体 | `.trae/agents/*.md` | `.claude/agents/*.md` | 无 → 提示词片段 | 无 → 提示词片段 | 无 → 提示词片段 |
| 编辑器钩子 | `.trae/hooks.json` | `.claude/settings.json` 的 hooks | 无 | 无 | 无 |
| 可靠门禁 | **git pre-commit**（所有平台通用，唯一必须装的一项） | 同左 | 同左 | 同左 | 同左 |

> **不确定的平台，一律按"未知"处理并问用户一次**：不要凭印象编造目录名。目录名写错比没有入口更糟。

### 2.1 一台设备装多个平台

同一份 `.harness/` 可以同时挂到多个平台目录，但**入口是生成物，不入库**（junction / symlink 不随 git 走）。

处理方式：**探测 + 告知 + 给一条可复制命令，不代建非当前平台。**

| 做 | 不做 |
| --- | --- |
| 安装时把入口建在**当前运行的平台**（否则技能根本不生效，这是安装的一部分） | 探到 `.claude/`、`.codex/`、`.codebuddy/` 就替用户全建一遍 |
| 列出探测到的平台目录、哪些已有 `skills/`、还差哪几个，并给出命令 | 静默创建一堆用户没打算用的平台目录 |
| 用户明确说"都给我挂上"时，再按平台逐个执行 | 把 junction 当成"装好了"的证据（换机器 / 重新 clone 就没了） |

Windows 用目录联接、macOS/Linux 用 symlink，失败时退化为带 `.harness-copy` 标记的复制：

```powershell
# 在当前项目根执行；-Dest 换成目标平台的技能目录
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\setup-links.ps1 -Dest .trae/skills
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\setup-links.ps1 -Dest .claude/skills
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\setup-links.ps1 -Dest .codex/skills
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\setup-links.ps1 -Dest .codebuddy/skills
```

> 告知的措辞要具体："已为 TRAE 建好入口；检测到 `.codex/` 和 `.codebuddy/`，要一起挂就用上面第 3、4 条命令。"——
> 不要只说"支持多平台"，那等于没说。

## 3. 三种技能发现模式（按优先级降级）

| 模式 | 条件 | 做法 |
| --- | --- | --- |
| **A 自动发现** | 平台会扫描某个固定目录 | 在那建链接/复制，指向 `.harness/skills/<类>/<技能>/` |
| **B 入口导入** | 平台有常驻文件且支持导入 | 在常驻文件里 `@` 导入真源，不复制内容 |
| **C 索引导航** | 没有任何自动发现 | 生成 `.harness/skills/INDEX.md`，并在常驻文件里写死：**做某类任务前必须先读对应技能** |

C 模式不是"降级版"就不算数：它的触发靠常驻文件里的**必读清单**，可靠性甚至高于 A（A 依赖平台匹配 description）。

## 4. 安装时的平台适配（5 步）

```text
1) 探测（只读）
   看仓库根是否有：.trae/  .claude/  .codex/  .codebuddy/  .cursor/
   看是否已有：AGENTS.md  CLAUDE.md  .cursorrules
   探测不到就问用户一次；仍不确定 → 按"未知"处理（模式 C）
   探测到多个：当前平台照常建入口，其余**只列出来 + 给命令**（见 2.1）

2) 落核心（平台无关，只补缺不覆盖）
   复制时用 Copy-Missing 语义：同名文件已存在 → 列 `[SKIP] conflict` 并读后合并，绝不覆盖
   复制 templates/scripts/*  →  scripts/
   复制 templates/.harness/{rules,wiki,modules,changes}/* → .harness/ 同名目录
   只复制 templates/.harness/skills/README.md → .harness/skills/README.md
   有 agents 目录的平台：复制 templates/.trae/agents/*.md → 平台 agents 目录（TRAE `.trae/agents`，Claude `.claude/agents`）
   （技能按启用集编译，不整目录复制；见 SKILL.md 第 0 步）

3) 写常驻入口
   TRAE / Codex / CodeBuddy / 未知 → AGENTS.md（薄，≤150 行）
   Claude Code                    → CLAUDE.md，首行写 @AGENTS.md，不要复制第二份内容

4) 建发现入口
   模式 A：在平台技能目录建链接 → .harness/skills/<类>/<技能>
           TRAE .trae/skills · Claude .claude/skills · Codex .codex/skills · CodeBuddy .codebuddy/skills
           只建当前平台；其余按 2.1 告知并给命令
   模式 B：确认常驻文件里的导入生效
   模式 C：生成 .harness/skills/INDEX.md，并把"必读清单"写进常驻文件

5) 装门禁（所有平台相同）
   git pre-commit → scripts/red-line-scan.*（只扫本次改动）
   再补一条 CI（堵 --no-verify）
```

## 5. 平台目录里只放什么

| 允许 | 禁止 |
| --- | --- |
| 指向 `.harness/` 的链接 | 复制技能正文副本（两份必然漂移） |
| 一行动态导入（`@AGENTS.md`） | 在 `CLAUDE.md` 里重写一遍规则 |
| 平台专用的钩子/agent 声明 | 把项目业务规则写进平台目录 |

**判断标准：删掉整个平台目录后，`verify-harness` 仍应能重建它；删掉 `.harness/` 则一切归零。**

## 6. 降级规则（平台缺能力时）

| 缺什么 | 降级做法 | 必须告知用户 |
| --- | --- | --- |
| 技能自动发现 | 模式 C：索引 + 必读清单 | "技能靠索引加载，不保证自动触发" |
| 编辑器钩子 | 只装 git pre-commit | "编辑器内没有即时反馈，错误要到提交时才拦" |
| 子智能体机制 | 把 reviewer 的检查项写进流程技能的"自检"节 | "没有独立 reviewer，靠自检清单替代" |
| 没有 git | 无门禁；改为交付前手工跑扫描 | "本次改动没有回滚手段，也没有强制门禁" |

## 7. 机制层怎么跨 OS 跑

| 脚本 | Windows | macOS / Linux |
| --- | --- | --- |
| `red-line-scan` | `.ps1`（默认，PS 5.1 自带） | `.py`（`python3`；两份的规则语义、退出码一致） |
| `install-git-hooks` | 生成 sh hook；hook **自己选解释器**：`powershell → python3 → python → pwsh` | 同左 |
| `probe-project` / `stage-gate` / `verify-*` / `setup-links` | `.ps1` | **未做路径分隔符适配**：这些脚本内部写的是 Windows 分隔符，在 macOS/Linux 上用 pwsh 会报路径不存在。要么先按平台改路径，要么按本文档手工核对，不要假装它们能跑 |

原则：**门禁必须跨平台可跑**（只依赖 git + 一个解释器）；体检脚本允许 Windows 优先，但文档里必须写明非 Windows 的替代做法，不能假装它能跑。

> 两份扫描器（`.ps1` / `.py`）是镜像实现。**改匹配逻辑必须同时改两份**，否则两个平台的门禁会悄悄不一致。

---

## 8. 校验

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-harness.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-grounding.ps1
```

`verify-harness` 的"平台入口"检查只要求：**至少存在一个可用的技能发现目录或索引**、**至少有一个子智能体入口或明确的降级声明**。
它不要求某个特定平台的目录存在——否则这套东西就又被绑死在一个 IDE 上了。

---

## 9. 与其它文档的分工

- `架构与职责.md`：内容分几层（常驻 / 按需 / 强制）
- 本文件：每层**放在哪个平台的哪个位置**
- `接地协议.md`：写进去的内容**凭什么可信**
- `落地策略.md`：存量项目**按什么顺序接入**
