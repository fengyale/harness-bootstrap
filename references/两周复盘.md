# 两周复盘清单（唯一能验证 A7 的方式）

> **A1–A5 落地即可验；A6 的第二层（趋势）与 A7 只能靠时间验**——A6 需要两个连续 14 天窗口，A7 看同一个错误会不会犯第二次。
>
> 建议：落地后第 **14 天**做一次，之后**每两周一次**（与 `维护与体检.md` 的退役检查同频）。每次 30 分钟。

---

## 一、先跑脚本出数（10 分钟）

不要凭印象，先让脚本说话：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\metrics.ps1 -Days 14
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\metrics.ps1 -Days 14 -Compare
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\metrics.ps1 -Days 14 -Json
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-harness.ps1
```

> `-Days 14` 只看最近两周；不加 `-Days` 是全部历史（看趋势用）。
> `-Compare` 把「最近 14 天」和「再往前 14 天」放在一起比，输出 `IMPROVING / REGRESSING / FLAT / INSUFFICIENT DATA`。
> **没有 `-Compare` 的复盘只是"这周怎么样"，有 `-Compare` 才是"它有没有在变好"。**
> 没有日期行的任务会回退到文件修改时间，并在输出里列为 `undated`，不会被静默丢掉。

| # | 指标 | 来源（脚本自动） |
| --- | --- | --- |
| 1 | 任务数、总纠正次数、平均纠正次数 | `.harness/changes/*/summary.md` 的 `corrections:` |
| 1b | **实现层纠正次数**（目标恒为 0） | `summary.md` 的 `impl_corrections:` |
| 2 | 门禁拦截次数 | `.harness/metrics/gate.jsonl` 的 `blocked=1` |
| 3 | **提交数 / 绕过数 / 绕过率** | `gate.jsonl` 的 `scanned` 字段（`--no-verify` 记为 0） |
| 4 | **技能加载率**、各技能加载次数、从未加载的技能 | `loaded_skills:` + `.harness/skills/` 实际清单 |
| 5 | **同一教训出现次数**（≥2 即升级信号） | `summary.md` 的 `lesson_id:`（metrics 输出里的 `lessons`） |

**趋势怎么读（`-Compare` 的四种结论）：**

| 结论 | 含义 | 下一步 |
| --- | --- | --- |
| `IMPROVING` | 平均纠正下降 ≥20%，且技能加载率没变差 | 保持；把已晋升的 `lesson_id` 记进 `.harness/lessons-promoted.txt` |
| `REGRESSING` | 纠正上升 ≥20%，或实现层纠正变多，或绕过率 >10% | **先查门禁是否被绕过**，再查哪条规则没加载 |
| `FLAT` | 两个窗口没有明显变化 | 问一句：是任务类型变了，还是框架没起作用？ |
| `INSUFFICIENT DATA` | 任一窗口任务数 < 2 | 多跑几个真实任务，不要用 1 次任务下结论 |

**仍需人工补充一项**：

- 装之前两周的基线（没有历史数据就估一个区间，别跳过）

> `lesson_id` 只解决"数得出"：第一次就把 id 定下来、第二次复用同一个 id，`metrics.ps1` 会直接报
> `lesson repeated 2x: <id> (promote it into a rule, a gate or a skill)`。
> 但"这两次算不算同一类"仍然由人判断——判断不了就起两个 id，不会误合并。

> `corrections:` 是自报字段——填 0 但实际被纠正了三次，整套度量就废了。

## 二、逐条判断（15 分钟）

### 2.1 重复出现的问题（最重要）

对第一节「指标表」#5 里"重复 ≥2 次"的每一类，填这张表：

| 问题类型 | 次数 | 为什么框架没挡住 | 该往哪补 |
| --- | --- | --- | --- |
| `<例：新增模块目录放错>` | 3 | ①没规则 ②有规则没加载 ③有规则AI没遵守 ④有门禁但没覆盖 | ①写进 `工程结构.md` ②改技能 description ③做成红线 ④加扫描规则 |

**四个原因对应四种修法，别搞混了：**

| 原因 | 说明 | 修法 |
| --- | --- | --- |
| ① **没规则** | 框架里压根没写 | 补进 `.harness/rules/` 或技能 |
| ② **有规则没加载** | 写了但 AI 没看到 | 检查是不是在常驻文件里；否则改成技能 + 改 description |
| ③ **加载了但没遵守** | 看到了没照做 | 写得更具体（给正反例）；或升级成门禁 |
| ④ **有门禁但漏了** | 扫描规则没覆盖 | 补 `red-line-rules.json` 的 pattern |

> **判断口诀：能写成 #4（门禁）的，就别停在 #1（文档）。**

### 2.2 技能体检

对**已装**的每个技能问三句：

| 技能 | 这两周被触发过？ | 触发了有用？ | 与代码还一致？ | 结论 |
| --- | --- | --- | --- | --- |
| `<name>` | 是 / 否 | 是 / 一般 / 没用 | 是 / 已失真 | 保留 / 改写 / **删除** |

**删除是合法结论。** 长期不触发 + 场景不存在 = 应该删。
> 与代码失真的技能**必须**马上改或删——它会自信地教错。

### 2.3 红线复核

| 检查 | 结果 |
| --- | --- |
| 每条红线这段时间真的触发过吗？ | `<红线条目 + 次数>` |
| 有哪条**从没触发过**？ | 是 → 可能写得不对（永真/永假），或者项目里确实没这问题 → **考虑删** |
| 有哪条**误报太多**，被人关掉了？ | → 用 `requireAlso` 收窄，或拆细 |

---

## 三、定下一步（5 分钟）

只做**三个决定**，不要贪多：

### 决定 1：补哪 1–2 个技能？

从"重复 ≥2 次但框架没覆盖"的问题里挑**最高频的一类**，补成一个技能。
> 一次只补 1–2 个。补 5 个的结果通常是一个都不好用。

### 决定 2：哪条从"文档"升级成"门禁"？

找一条**这段时间被违反过、且能机器判定**的规则，写进 `red-line-rules.json`。
> 这是把"教训"变成"机制"的唯一动作。

### 决定 3：删什么？

- 长期不触发的技能
- 从没触发过的红线
- 与代码已失真的文档

> **不删，库就会腐化。腐化的库比没有更坏。**

---

## 四、结论（三条，写下来）

```markdown
## 两周复盘（<日期区间>）

**纠正次数**：<装前> → <装后>（降了 <X>%）
**重复问题**：<N> 类，其中已修 <M> 类

**这次的三个决定**
1. 补技能：<name> —— 因为 <高频问题>
2. 升级门禁：<红线> —— 因为 <被违反过且可判定>
3. 删除：<技能/红线/文档> —— 因为 <长期不触发/已失真>

**下一个两周要看什么**：<一个具体指标>
```

---

## 五、如果复盘结论是"没起作用"

**这也是有效结论**，而且很常见。按这个顺序排查：

| 症状 | 最可能的原因 | 先查 |
| --- | --- | --- |
| 技能从没自动触发 | `description` 写的是你的说法，不是用户会说的话 | 跑 `维护与体检.md` 提示词 D |
| AI 看到了规则但不遵守 | 规则写的是"要优雅"这类不可判定的词 | 改成可判定 + 给正反例 |
| 门禁从没拦过 | 没装 hook，或扫描范围错了（0 文件） | 跑 `verify-harness.ps1` 看 gate / runnable 两项 |
| 用户觉得比原来更累 | 规则太厚、技能太多、流程太长 | 砍到只剩核心 3 个技能 + 5 条红线，重来一次 |
| 一切正常但没有改善感 | 可能本来就没那么痛，或改善发生在别处 | 对比第 1 节的两个数字，别靠感觉 |

> **最后一种情况要诚实面对**：如果装之前纠正次数本来就不高，那这套东西的收益就是有限的。
> 那不是失败，是**这个项目此刻不需要这么重的框架**——裁到最小，或者先不装。

---

## 六、复盘之后

**如果 A7 成立**（同类错误不再重复），说明闭环通了，进入维护节奏：
- 每两周做一次本复盘（30 分钟）
- 每两周按 `metrics.ps1 -Days 28` 列退役候选，**人确认后**才删技能/红线；每季度做一次结构审视 + 重构

**如果 A7 连续两次不成立**，别再往上加东西，回到 `references/落地策略.md` 重看一遍——
多半是**启用集太重**或**门禁没生效**，而不是"技能不够多"。
