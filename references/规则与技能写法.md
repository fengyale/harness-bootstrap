# 规则与技能写法

> 写 `SKILL.md`、写红线、调 description 时读这份。

## 一、`SKILL.md` 标准模板

```markdown
---
name: <kebab-case，与目录名一致>
description: <做什么 + 关键技术点>。当 <具体场景 / 用户会说的原话> 时使用本技能<，可选：什么情况下禁止/必须>。
---

# <技能名>
（一句话定位 + 「对应流程**阶段 X**」这类坐标）

## 触发条件
- 用户会说的那几句话（照抄真实口语，匹配率最高）
- 什么时点必须用

## 前置准备
- 依赖的上游产出（L2/L3 的 `.harness/changes/<特性>/summary.md`、L1 的 `_small.md` 行必须已存在；否则退回上一阶段）
- **加载范围与超限例外**：默认读什么、技能不占额度、超限怎么留痕
  | 情况 | 加载 |
  | 涉及表结构变更 | `.harness/wiki/数据模型.md` |

## 核心规则
1. **加粗编号**，不可协商
2. …

## 执行流程
### Step 1 - xxx
（表格 或 可直接套用的代码/配置模板；标注"模式来自 <真实文件>"）
### Step 2 - xxx
…Step N

## 自检清单
- [ ] 每条都能用眼睛或脚本判定（"所有缓存操作被 try-catch 包裹" ✅ /"代码要优雅" ❌）

## 红线
- ❌ …
- ❌ …

## 下一步
（指向下一个技能 / 阶段）
```

**四个不能省的要点**：

1. **触发条件写进 `description`**（不只是正文）——因为常驻目录里只有 `name` + `description` 会被看见。
2. **`前置准备` 要有"上游产出不存在就退回去"**——这是阶段之间的咬合。
3. **`自检清单` + `红线` 是收尾两段**——这是"可校验"的落点。
4. **代码示例要标注来源**（"模式来自 XxxServiceImpl"），让模型照抄项目真实形状。

## 二、`description` 怎么写（决定触发命中率）

- 格式：`<做什么 + 关键技术点>。当 <具体场景 / 用户原话> 时使用本技能。`
- **把用户会说的原话写进去**（"这个接口太慢了""加个 Redis"），而不是书面语
- **必须短**（平台会截短 `description`）
- **不同技能的触发词不能重叠**——写新技能前先读一遍所有已有技能的 description
- 想验证命中率 → 用 `维护与体检.md` 的提示词 D

## 三、红线怎么写（必须可机器判定）

每条红线**三处同步**，缺一不可：

| 位置 | 作用 |
| --- | --- |
| 根 `AGENTS.md` 的「🔴 红线」表 | 每轮在场，模型随时看得见 |
| `.harness/rules/编码规范.md` 的「红线汇总」 | 详细依据 + 例外说明 |
| `scripts/red-line-rules.json` | **真正能拦住你的那一处** |

要求：

- 每条红线给出**可执行的检查动作**（搜什么、看哪里），否则它只是口号
- 上例：`金额字段 → 全局搜 Double|BigDecimal|float + 金额语义字段；DDL 搜 DECIMAL|FLOAT`
- 误报要压：`red-line-rules.json` 里可用 `requireAlso`（同一行必须同时命中才算违规）
- 红线数量控制在 **8 条以内**——多了没人记得住，也会互相冲突

## 四、技能命名与目录规则

- `.trae/skills/` **只扫一层** → 技能名**必须全局唯一**（`main-dev` 与 `biz-dev` 下不能同名）
- 真源路径：`.harness/skills/<分类>/<技能名>/SKILL.md`
- 技能可以带附属文件（模板、示例、脚本），放在技能目录下的子目录里
- 技能名用 kebab-case；frontmatter 的 `name` 与目录名保持一致

## 五、规则文件（`.harness/rules/`）的写法

- 三份足矣：**编码规范**（单文件内怎么写）、**工程结构**（放哪、怎么命名、依赖方向）、**开发流程规范**（阶段、质量门、AI 编码纪律）
- **无 frontmatter**；结构固定为一句话定位 → `##` 主题 → `###` 子规范
- 以 **Markdown 表格**为主；配 ✅ 正确 / ❌ 错误 成对示例
- **🔴 = 红线（零容忍）、🟡 = 强烈建议** —— 图例在「编码规范」开头定义一次，全局统一
- 关键文件末尾必留「红线」或「质量检查点」清单

## 六、AI 编码纪律（写进「开发流程规范」，也可摘要进 `AGENTS.md`）

| 项 | 内容 |
| --- | --- |
| 加载范围 | 默认只读「本任务涉及的模块卡 + 直接相关的 1–2 份 wiki / 规则」；**技能与模块卡不占此额度**，按流程必上 |
| 超限例外 | 跨模块 / 数据迁移 / 上线评审可多读，但须在 `summary.md` 写一行「额外读取：… ｜ 原因：…」 |
| 变更量阈值 | 单次变更 **≤ 文件总量的 40%**，超过必须拆分 |
| 每次验证 | 改完必须过编译 / 类型检查（命令见 `AGENTS.md`） |
| 质量检查点 | 0 error、0 🔴 violation、覆盖率达标、0 🔴 issue、CI 全绿 |
| 红线冲突处理 | 立即停止 → 修复 → **从受影响阶段重新验证**；禁止"先合入后续再改" |
| 熵管理周期 | 每日红线扫描 / 每周依赖审计 / 每两周架构审视 + 退役候选 / 每月技术债 + 技能体检 / 每季度重构 |
