# 接地协议（Grounding Protocol）

> **一句话**：安装后不是"把模板写满"，而是**从项目里取证**，再把证据写进资产。
> 没有证据的内容，写得再像也不许进技能正文——那会变成"自信地教错"。

---

## 1. 三条硬规则

| # | 规则 | 违反的后果 |
| --- | --- | --- |
| **G1** | **只读既有资产**：已有 `AGENTS.md` / `CLAUDE.md` / `.cursorrules` / 规则文件 / 已有技能，**只读，不覆盖**；有冲突只出 diff 建议 + 人工确认点 | 一次覆盖就毁掉用户最贵的东西 |
| **G2** | **无 E1/E2 证据不得写入技能正文**（只能写进 `TODO(待确认)`）。**唯一例外**：新项目模式（`.harness/project-brief.md` 存在且尚无代码）可用 E0 用户确认代替 | 产出看起来满分、实际全是幻觉 |
| **G3** | **冷启动配额**：首次安装 **3–5 个**技能（硬上限 8）；具体挑哪几个见 `落地策略.md` 第一节「默认启用集」；**运行期不设数量上限**，改按加载率删减（连续 28 天 0 加载 → 列候选，**人确认后**才删）。单文件 ≤ 120 行 | 全量"完善"一遍 = 全量失真一遍 |

---

## 2. 证据分级

| 级别 | 定义 | 能否进正文 |
| --- | --- | --- |
| **E0** | 用户确认：带确认人与日期的明确答复 | ✅ **仅新项目无代码阶段**；代码出现后必须升级为 E1/E2 |
| **E1** | 机器可验证：跑得通的命令、脚本输出、测试结果 | ✅ 直接引用 |
| **E2** | 代码事实：真实存在的文件/符号（路径 + 行号） | ✅ 直接引用 |
| **E3** | 文档陈述：README、注释、他人说法 | ⚠️ 必须标注来源，且不得当成"已验证" |
| **E4** | 推断：从命名、结构、经验推出来的 | ❌ 只能进 `TODO(待确认)` |

> **E0 的边界**：它只证明"人和智能体对项目的理解对齐了"，不证明"代码里确实这样"。
> 判定分三种，不要混：
> - **没有 `.harness/project-brief.md`**（存量项目模式）出现 E0 → **FAIL**，那时应该能指到文件和行号。
> - **有 brief 但代码还没落地** → E0 合法，`verify-grounding` 只报 WARN（新项目起点）。
> - **有 brief 且源码目录已有真实文件** → E0 只报 **WARN 要求升级**；它不再是长期通行证，新代码的第一个任务必须把 E0 换成 E1/E2。

> 判断"非显然约定"的唯一标准：**这条内容能不能从框架文档里推出来**。能推出来的，是通用最佳实践，不要写；推不出来的，才是这个项目的资产。

## 3. 证据锚点（机器可解析，格式不可改）

技能正文里，每条项目专属结论后面紧跟一行锚点：

```
- [E0] confirm:<确认人> <YYYY-MM-DD> :: <确认了什么>
- [E1] cmd: <命令> :: <这条命令证明什么>
- [E2] <相对路径>#L<起>-L<止> :: <这个文件/这段代码证明什么>
- [E3] <文档相对路径> :: <这份文档声称什么，尚未被代码验证>
- [E4] 无 :: <为什么暂时无法取证>
```

约束：

- 路径一律相对项目根目录，**正斜杠/反斜杠都行**，脚本会统一
- `#L12-L40` 可省略，但写了就要对
- 锚点行必须独占一行，以 `- [E0]` / `- [E1]` / `- [E2]` / `- [E3]` / `- [E4]` 开头（脚本按此正则扫描）
- **每个接地的 SKILL.md 至少 1 条 E1/E2 锚点**；一条都没有 = 未接地技能，脚本报 WARN。
  **E3 只是转发文档说法，永远不算接地**，脚本会报 WARN 要求回代码核实
- **新项目无代码阶段**可用 E0 代替，但脚本仍报 WARN 提醒升级——它不是长期通行证
- 每条锚点写"证明什么"，不要写"参考"
- 写一行 `- verified: YYYY-MM-DD`：重读代码后更新日期。`verify-grounding` 会对比它和
  E2 目标文件的修改时间，代码更新在后就报 `stale`（WARN）——这是技能"保鲜"的唯一机制

## 4. 从探测到接地的五步

1. **探测**：`scripts\probe-project.ps1` → `baseline.json`（技术栈、命令、目录、冲突清单）
2. **列证据清单**：把"这个项目里不这么做会炸"的候选逐条列出，每条标 E1/E2/E3/E4
3. **人工确认**：只把 E1/E2 的候选交给用户确认（业务取舍必须人来拍板）
4. **写 3–5 个技能**：只写确认过的，其余保持"未接地"，在正文顶部写 `- [E4] 无 :: 通用骨架，本项目未接地`
5. **校验 + 试跑**：`scripts\verify-grounding.ps1` → 0 FAIL；然后立刻跑一个真实小任务，记录纠正次数

> 第 5 步不是可选项。**A7（同一个错误不犯第二次）从第一次真实任务开始计数**，不是两周后才开始看。

> **新项目（仓库里还没有代码）走另一条前置路径**：先按 `references/新项目初始化.md` 与用户逐项确认
> 项目背景、业务边界、技术选型，产出 `.harness/project-brief.md`。这个阶段的证据只有 E0。
> **代码落地的第一个任务，就要把 E0 逐条升级成 E1/E2**——否则脚本会一直报 WARN。

---

## 5. 什么时候**拒绝**写

- 探测不到 E1/E2（比如项目没有可跑的构建命令、没有可引用的实现）→ 只出"待确认清单"，不生成技能
- 与既有规则冲突 → 停下来出 diff，让用户选
- 结论依赖业务判断（红线松紧、是否补短板）→ 提议，不落地
- 只能写出通用最佳实践 → 不写。**"没有这条技能"比"有一条假技能"安全**

## 6. 接地技能的单条写法（四字段）

```
### <一条断言，陈述句，可判定>
- 根因：<不这么做会发生什么，来自真实事故或代码结构>
- 证据：
  - [E2] src/main/java/.../XxxService.java#L40-L58 :: 现有实现就是这么处理事务的
- 校验：<怎么机器判定：编译 / 测试 / 扫描规则 / 人工确认点>
```

正例（有证据、有根因、可判定）：

```
### 缓存失效必须与业务事务同层提交
- 根因：先删缓存再提交，提交失败会留下脏读窗口
- 证据：
  - [E2] src/main/java/.../OrderServiceImpl.java#L88-L96 :: 同类逻辑用的是 afterCommit
- 校验：review 时搜索 delete 调用是否在事务外
```

反例（不许写）：

```
### 使用 Cache-Aside 模式
（没有根因、没有证据、无法判定——模型本来就知道，写了只会增加上下文）
```

## 7. 校验

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-grounding.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\verify-grounding.ps1 -Root D:\proj
```

它检查六类问题：

1. **编译契约**——技能里是否残留 `<!-- slot:` 未填标记，是否提到了 `stack.json` 里没有的技术
2. **引用完整性**——技能里出现的 `.harness\` / `.trae\` / `scripts\` / `AGENTS.md` 路径是否真实存在（这条能抓住拼写错误、改名残留、路径失效）
3. **锚点有效性**——E2 锚点指向的文件是否存在；E1 锚点是否为空；E0 的格式是否合法、是否出现在非新项目模式
4. **接地**——每个技能是否至少有 1 个 E1/E2 锚点（新项目无代码阶段 E0 可暂代并报 WARN）
5. **配额**——接地的技能数（冷启动 `-MaxGrounded`）与单文件行数（>120 行直接 FAIL）
6. **保鲜**——E2 指向的代码改过之后，技能有没有重新核对过

`verify-harness.ps1` 会调用它（第 8 项检查），所以正常流程跑一次就够。

---

## 8. 与"自建指南"的分工

- `自建指南.md` 管**怎么设计**（结构、分层、技能怎么拆）
- 本协议管**凭什么写**（证据、配额、拒绝条件）
- 两者冲突时：**本协议优先**——宁可少写，不可假设
