# 新项目初始化（Before the first line of code）

> **适用**：仓库里还没有可运行代码，或只有脚手架（空 `src/`、只有 README、只有 `pom.xml`）。
> **不适用**：已有业务代码的半道项目 → 走 `references/自建指南.md` 的「存量加固」。
>
> **一句话**：存量项目靠**读代码**取证；新项目靠**问对人**取证。两者都不能靠猜。

---

## 1. 为什么单列一条路径

存量项目的证据来自 E1（可跑命令）/ E2（真实代码）。新项目这两样都不存在。
如果硬套同一套流程，智能体只有两个选择：编造，或什么都不写。两种都是失败。

新项目的正确做法是：**先把"我们要做什么"问到双方颗粒度一致，把答案落成
`.harness/project-brief.md`，用 E0（用户确认）作为临时证据；代码一落地就升级为 E1/E2。**

> E0 不是免检通行证。它的作用只有一个：记录"这个结论是人确认过的，不是模型编的"。
> 格式与边界见 `references/接地协议.md` 第 2 节。

---

## 2. 进入条件（三选一）

- 用户明说"新建项目 / 从零开始"
- `probe-project.ps1` 产出的 `baseline.json`（默认在仓库根 `baseline\`；也接受 `.harness\baseline\`）里 `srcRoots` / `testRoots` **列出的目录下都没有真实文件**（空 `src/` 目录不算源码），且没有任何可运行的业务代码（只有 `pom.xml` / `package.json` 等构建文件也算新项目）
- 仓库只有脚手架：文件类型里没有业务源码扩展名（`.java` / `.ts` / `.go` / `.py` 等），或只有模板生成的空文件

**不确定就问用户一次**："这个仓库现在是新项目，还是已有代码的半道项目？"
问错路径的代价是整份 harness 内容错位。

---

## 3. 五轮确认（每轮都要有结论，不许跳过）

> 原则：**一轮只问一类问题**，一轮结束就复述给用户确认。
> 用户说"你定"时，给出 2–3 个选项 + 推荐项 + 影响，让他在选项上拍板，而不是替他拍板。

### 第 1 轮 · 项目与背景

问：解决什么问题、给谁用、成功长什么样、明确的非目标是什么。

产出字段：
- 项目名 / 一句话定位
- 目标用户与核心场景（3 条以内）
- 本阶段**不做**什么（非目标，防止后续无限扩张）
- 成功判据（可观察，不是"好用"）

### 第 2 轮 · 业务边界与关键规则

问：核心领域对象有哪些、它们之间什么关系、哪些规则**绝对不能错**（钱、库存、权限、时效）。

产出字段：
- 领域术语表（术语 → 含义 → 是否已定）
- 核心实体与关系（先文字，后画图）
- 业务红线候选（会写进 `AGENTS.md` 的红线表）
- 状态流转（如果有）

> **这一轮决定后面技能写什么。** 宁可多问一句"这个状态允许回退吗"，不要事后靠猜。

### 第 3 轮 · 架构与技术选型

问：语言/框架/数据库/缓存/消息/前端，部署形态，团队已有什么经验。

产出字段：
- 技术栈表（与 `AGENTS.md` 的「技术栈」一一对应）
- 目录结构约定（谁放哪、依赖方向）
- 构建 / 测试 / 启动命令候选（**标记为"待实测"，落地后必须真跑一次**）
- 明确排除的技术（例如"不用 MyBatis-Plus""不引入 MQ"）

### 第 4 轮 · 非功能与工程约束

问：预期量级、并发、可用性、数据一致性要求、安全与合规、日志与观测。

产出字段：
- 量级与性能目标（可判定的数字）
- 一致性要求（哪些操作必须强一致）
- 安全约束（鉴权、敏感数据、审计）
- 观测手段（日志 / 指标 / 告警）

### 第 5 轮 · 验收与交付方式

问：第一个里程碑是什么、怎么算完成、谁来验、出问题怎么回滚。

产出字段：
- 里程碑 1 的验收清单（可勾选）
- 交付节奏（谁在什么时候看什么）
- 回滚预期（新项目通常"删库重建"，但要写明）

---

## 4. 对齐颗粒度（什么时候可以停）

五轮问完，做一次**复述校验**：用 10 行以内复述项目是什么、核心规则是什么、第一里程碑做什么，
让用户回答"对 / 不对，改这里"。

- 用户能只靠这段复述判断对错 → 颗粒度够了
- 用户说"大概是这个意思" → 不够，回去补具体项
- 还有 `TODO(待确认)` 落在**业务红线**或**技术栈**上 → 不许开工

---

## 5. 产出：`.harness/project-brief.md`

> 它是"新项目模式"的判定标志（`verify-grounding.ps1` 用它识别 E0 是否合法）。
> **必须真的写到这个路径**，不要换个名字。

模板（复制后按实际填写，没有答案的写 `TODO(待确认)`）：

```markdown
# 项目简报（Project Brief）

- 状态：已与用户确认（E0）
- 确认人：<姓名/角色>
- 确认日期：<YYYY-MM-DD>
- 复述校验：用户已确认（第 4 节）

## 1. 定位

- 一句话：<解决什么问题，给谁用>
- 目标用户：<...>
- 非目标：<本阶段明确不做的事>

## 2. 业务

- 领域术语：<术语 → 含义>
- 核心实体：<实体 → 关键字段 → 关系>
- 业务红线候选：<R1..Rn 一句话一条>
- 状态流转：<...>

## 3. 技术

- 技术栈：<语言 / 框架 / 数据库 / 缓存 / 消息 / 前端>
- 目录约定：<...>
- 命令（待实测）：<build / test / lint / run>
- 明确排除：<...>

## 4. 非功能

- 量级：<...>
- 一致性：<...>
- 安全：<...>
- 观测：<...>

## 5. 里程碑 1

- 验收清单：<...>
- 交付节奏：<...>
- 回滚预期：<...>

## 6. 未决项

- <TODO(待确认)：...>
```

---

## 6. 写完 brief 之后做什么

1. **写 `AGENTS.md`**：技术栈、必跑命令（标"待实测"）、红线候选、文件索引、AI 编码纪律。
   命令在第一次真正跑通后立刻改成实测值。
2. **写 3–5 个技能**，每条项目结论后跟 E0 锚点：

   ```
   - [E0] confirm:<确认人> <YYYY-MM-DD> :: <确认了什么>
   ```

   例：`- [E0] confirm:产品负责人 2026-11-02 :: 库存扣减必须先冻结再扣减，不允许负库存`

3. **写规则三件套的骨架**：`编码规范` / `工程结构` / `开发流程规范`。
   内容以 brief 为准；brief 没写的，写 `TODO(待确认)`，不许编。
4. **装门禁**：`install-git-hooks.ps1`。新项目第一行代码就该有红线扫描。
5. **跑校验**：`verify-harness.ps1` + `verify-grounding.ps1`。
   此时出现 `E0 confirmations only` 的 WARN 是**预期内**的，不是失败。

---

## 7. E0 的退出条件（必须写进第一个任务）

代码落地后的**第一个真实任务**，在 `summary.md` 里加一条：

```
- 接地升级：把 <技能名> 的 E0 锚点替换为 E1/E2（依据：<命令输出 / 文件路径#行号>）
```

判定：
- 仓库已有源码（`baseline.json.srcRoots` / `testRoots` 里至少一个目录下存在**真实文件**——只有空目录不算源码；根目录或 `.harness\baseline\` 两种布局都算）而技能仍只有 E0 → `verify-grounding` 报 WARN
- 非新项目模式出现 E0 → **FAIL**（这条没有例外）

---

## 8. 不要做的事

- **不要**在五轮确认前生成任何技能或规则正文（那只是在写小说）
- **不要**一次生成全部 25 个技能；新项目默认 3–5 个，其余按需再长
- **不要**把"待实测"的命令写进 `AGENTS.md` 而不标记
- **不要**把 brief 当成一次性文档：需求变更、选型变更都要回写，并更新确认日期
